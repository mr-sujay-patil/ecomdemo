## 5. ❗ A regression this phase introduced, and only the smoke test found it

**Both other suites were green while the notification consumer's partition was completely
stopped.** This is the most useful thing that happened in the phase and is worth reading in full.

### What was written

The relay needs to send the payload as raw bytes, so it needs a producer with a
`StringSerializer` rather than the application's `JsonSerializer`. The obvious way to get one is
a second `@Bean` of type `KafkaTemplate`. That is what the first draft did.

### What it actually did

Two failures that compound, neither visible at startup:

1. Spring Boot auto-configures its `kafkaTemplate` under
   `@ConditionalOnMissingBean(KafkaTemplate.class)`. **Any** template bean — whatever its name,
   whatever its generics — makes Boot back off. So declaring one silently deleted the
   application's own template from the context. Nothing failed, because by this point nothing
   in the application publishes through it directly any more.

2. Spring Kafka's `DeadLetterPublishingRecoverer` resolves a template **by type** to publish to
   the retry and dead-letter topics. It found the only one left — the relay's — and tried to
   send an `OrderPlacedEvent` through a serializer that accepts only strings:

       org.springframework.kafka.KafkaException: Dead-letter publication to
       orders.placed-retry-0 failed for: orders.placed-0@35
       Caused by: java.lang.ClassCastException: class
       com.ecomdemo.messaging.OrderPlacedEvent cannot be cast to class java.lang.String

The consequence was worse than a failed send. The recoverer could not move the poison record
anywhere, so its offset was never committed and **the whole partition stopped** — head-of-line
blocking, precisely what Phase 17's retry topics exist to prevent, reintroduced by a bean in a
different package.

### How it surfaced

    Summary: 266 passed, 4 failed
      FAIL  a poison message ends on the dead-letter topic          expected True, actual False
      FAIL  and it is still notified, so the poison never blocked   expected 1,    actual 0
      FAIL  the notification consumer group has caught up (lag 0)   expected 0,    actual 2
      FAIL  flyway_schema_history shows V1-V9                       (the trivial one)

Three of those four are one fault. `./mvnw clean verify` was green throughout, and so was the new
`OutboxRelayKafkaIT`: catching this needs two templates **and** a poison message in the same
running system, which only the smoke test has.

### The fix

`OutboxKafkaSender` now owns its producer privately — it is not a `KafkaTemplate` bean at all —
and closes it on shutdown through `DisposableBean`. There is exactly one template bean in the
context again, Boot's, and it is the one the retry machinery finds. `@RetryableTopic` also names
it explicitly (`kafkaTemplate = "kafkaTemplate"`), so a third template added later cannot silently
re-point the recoverer.

`KafkaTemplateWiringTest` is the cheap version of this lesson: it asserts that Boot's template
exists and that it is the only one, and fails in seconds instead of in a ten-minute smoke run. It
does not prove the recoverer works; it proves the precondition that broke it is gone.

**The lesson worth keeping:** adding a bean is not a local change. `@ConditionalOnMissingBean` and
resolution-by-type make the bean factory a shared namespace, and a bean added for one feature can
silently reconfigure another that never mentions it.

## 6. Two smaller traps

**Boot 4 is Jackson 3; spring-kafka's `JsonDeserializer` is Jackson 2.** The payload is a Kafka
message body, so it must be written by the mapper that message will be read by —
`JacksonUtils.enhancedObjectMapper()`, not the auto-configured `JsonMapper`. The two disagree
about whether an `Instant` is an ISO-8601 string or an epoch decimal, and a mismatch fails nowhere
in the build: it fails at the consumer, at run time, on a message the producer considers perfectly
good. `OutboxWriterTest` round-trips the payload through the consumer's mapper to pin this down,
and the mapper is constructed inside `OutboxWriter` rather than injected, because which mapper
writes it is a correctness requirement and not a configuration choice.

**Spring counts every declared constructor, private ones included.** Adding a package-private
constructor "for tests" alongside the real one gave `No default constructor found` at startup. The
test mocks `OutboxKafkaSender` instead, which is what it wanted anyway — the relay's bookkeeping
is the subject there, not the serializer.

**`KafkaProperties.buildProducerProperties()` is the wrong source for the relay's settings.** Boot's
`@ServiceConnection` supplies the container's random broker address as connection *details*,
applied while the producer factory is built and never written back into the properties object.
Copying the auto-configured `ProducerFactory`'s own map is what makes the relay talk to the same
broker as everything else under test — and it inherits `acks=all` and `enable.idempotence=true`
without restating them, so they cannot drift from Phase 17.

## 7. What this phase deliberately did NOT solve

**Two instances would both publish.** The relay takes no lock, so two application instances polling
the same table can read the same pending row and both send it. That is survivable rather than
broken, and only because of the work Phase 17 did first: the duplicate carries the same
`event_id`, and `processed_event` on the consumer side refuses it. The cost is duplicate *sends*,
not duplicate notifications.

The proper fix is `SELECT ... FOR UPDATE SKIP LOCKED`, which hands each relay a disjoint set of
rows. It is left out here because it is a PostgreSQL-flavoured query the H2 unit suite could not
run, and because a lock is the wrong thing to introduce in the phase whose subject is durability.
Recorded in `docs/decisions.md` as deferred, not as solved.

**The outbox creates duplicates by design.** A relay that publishes a row and dies before
committing the mark will publish it again. That is the at-least-once seam and it is deliberate —
proved on purpose in `OutboxRelayKafkaIT.republicationIsAbsorbedByTheConsumer`, which un-marks a
published row and asserts that the republication costs a duplicate send and not a second
notification. Exactly-once at the producer would be a promise that lies.

**Ordering holds only while sends succeed in sequence**, which is why the batch stops at the first
failure. If it carried on, event N+1 would be published while event N was still pending, and N
would arrive later than the event that logically follows it.
