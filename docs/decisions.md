# Decision Log

> One or two lines per decision. Newest at the bottom. Format:
> `[Phase XX] Decision: … | Reason: … | Alternatives considered: …`

[Phase 00] Decision: Merge commits only, no branch deletion | Reason: preserves full phase history and enables ancestry-based merge verification | Alternatives considered: squash merge (rejected: breaks verification)
[Phase 00] Decision: Per-phase docs with a checkpoint file | Reason: keeps each Claude Code session's context small and resumable | Alternatives considered: single roadmap file
[Phase 00] Decision: Repository is public and named `ecomdemo`; the earlier attempt was renamed to `EcomDemo-archive` | Reason: GitHub repo names are case-insensitive, so the old `EcomDemo` blocked the name | Alternatives considered: reusing the old repo (rejected: its `main` already holds ~22 phases of divergent work)
[Phase 00] Decision: Branch protection on `main` with `enforce_admins: true` | Reason: without it GitHub exempts the owner, so "a direct push to main is rejected" would be false for the only person who pushes | Alternatives considered: protection without admin enforcement
[Phase 01] Decision: Spring Boot 4.1.1 on Java 21 | Reason: latest stable 4.x on start.spring.io at the time; Java 21 is the stack's LTS baseline even though JDK 25 is installed locally | Alternatives considered: Boot 4.2.0-M1 (rejected: not GA)
[Phase 01] Decision: Order lines snapshot product name and price, and the order stores its total | Reason: an order is a historical record and must survive repricing or deletion of a product | Alternatives considered: a @ManyToOne to Product with the total derived on read (rejected: rewrites history)
[Phase 01] Decision: The cart total is always derived, never stored | Reason: a stored total is a second source of truth that goes stale when a price or quantity changes | Alternatives considered: a cached total column
[Phase 01] Decision: Lazy associations plus explicit JOIN FETCH queries, and cart writes re-read before mapping | Reason: `save()` on a detached entity merges and returns a copy whose lazy associations are uninitialised proxies, which threw LazyInitializationException; the alternative fix, `@Transactional`, is Phase 6's scope | Alternatives considered: EAGER fetching (rejected: N+1 on every read), @Transactional (deferred to Phase 6)
[Phase 01] Decision: Checkout validates stock for all lines before writing any, but is not yet atomic | Reason: keeps the common failure clean without pulling Phase 6's transaction work forward; the remaining race is the reason Phase 6 exists | Alternatives considered: adding @Transactional now (rejected: out of phase scope)
[Phase 01] Decision: Orders map to table `orders` | Reason: ORDER is a reserved SQL word and an unquoted `insert into order` is a syntax error | Alternatives considered: quoting the identifier everywhere
[Phase 02] Decision: Test at four levels — Mockito unit tests, `@WebMvcTest`, `@DataJpaTest`, and the Phase 1 `@SpringBootTest` | Reason: each slice loads only what it tests, so a failure names its own layer and the suite stays fast (79 tests in ~9s) | Alternatives considered: `@SpringBootTest` everywhere (rejected: slow, and a failure could come from any layer)
[Phase 02] Decision: `MockMvcTester` rather than classic `MockMvc` + Hamcrest matchers | Reason: it is the AssertJ-native MockMvc API in Spring Framework 7, so every assertion in the project reads the same way | Alternatives considered: `mockMvc.perform(...).andExpect(status().isOk())` (rejected: a second assertion vocabulary to learn)
[Phase 02] Decision: Web tests assert the JSON body, not a deserialised DTO | Reason: `BigDecimal.equals()` compares scale as well as value, so a price serialised as 8999.00 and read back as 8999.0 fails an equality check that has nothing to do with the endpoint; JSONAssert compares numbers by value | Alternatives considered: comparing records (rejected: brittle for money), custom comparators (rejected: hides the wire format)
[Phase 02] Decision: `@DataJpaTest` covers only the hand-written `@Query` methods | Reason: everything else on `JpaRepository` is Spring Data's code, and testing a framework's own `findById` adds maintenance without adding confidence | Alternatives considered: testing every repository method
[Phase 02] Decision: Repository tests run with `spring.sql.init.mode=never` | Reason: a repository test should own the rows it asserts on; inheriting `data.sql` would couple the tests to the seed catalogue and break them whenever it changes | Alternatives considered: asserting against the seeded 10 products
[Phase 02] Decision: Generated ids are set reflectively in `TestData` | Reason: several rules key off a product id, and adding `setId()` to the entities purely for tests would let production code invent ids | Alternatives considered: a test-only setter (rejected: weakens the model), mocking the entities (rejected: hides real behaviour like `reduceStock`)
[Phase 02] Decision: Surefire loads the Mockito agent with `-javaagent` | Reason: Mockito self-attaches its bytecode agent today with a warning, and a future JDK will refuse dynamic attachment outright, which would fail the whole unit suite | Alternatives considered: suppressing the warning (rejected: postpones a breakage)
[Phase 03] Decision: springdoc-openapi 3.1.1 | Reason: first GA line built against Spring Boot 4 / Spring Framework 7 (its parent pom builds on Boot 4.1.0); the 2.x line targets Boot 3 | Alternatives considered: springdoc 2.8.x (rejected: wrong Boot generation), hand-written OpenAPI YAML (rejected: drifts from the code)
[Phase 03] Decision: Code-first — the spec is generated from the controllers and DTOs | Reason: one codebase and one author, so a generated document can never disagree with the code it describes | Alternatives considered: contract-first with generated stubs (rejected: its payoff is several teams agreeing on an API before writing code)
[Phase 03] Decision: Document metadata lives in an `OpenAPI` bean (`OpenApiConfig`), not `@OpenAPIDefinition` | Reason: the values are ordinary Java and can later come from configuration or the build, e.g. the version from a release tag | Alternatives considered: the annotation on the application class (rejected: constants only)
[Phase 03] Decision: `@Schema` carries descriptions and examples only; validation rules are not restated | Reason: springdoc already derives `required`, `maxLength` and `minimum` from the Bean Validation annotations, and restating them creates two sources of truth that can disagree | Alternatives considered: spelling out every constraint in `@Schema`
[Phase 03] Decision: Every `@Content` on an error response names `mediaType = "application/json"` | Reason: `@Content` with only a schema documents the body as `*/*`, while `GlobalExceptionHandler` actually returns JSON; the smoke check caught the mismatch | Alternatives considered: leaving the default (rejected: the document would be wrong)
[Phase 03] Decision: The spec is guarded by an automated test as well as the smoke script | Reason: `OpenApiDocumentationTest` fails the build when a controller is added without annotations, instead of waiting for someone to run the smoke test against a live app | Alternatives considered: smoke checks only (rejected: not run by `verify`, and CI arrives in Phase 11)
[Phase 03] Decision: `/v3/api-docs` and Swagger UI stay enabled, accepting springdoc's two startup WARNs | Reason: an explorable API is the point of the phase and there is no production profile yet; springdoc only warns that an open spec reveals the API's shape | Alternatives considered: disabling them (rejected: defeats the phase), a profile switch (deferred: Phase 8 decides access)
[Phase 04] Decision: PostgreSQL 18 from the official `postgres:18-alpine` image, started with one `docker run` | Reason: no installation to undo, the same image the later Docker Compose and Kubernetes phases will use, and the data lives in a Docker volume so it survives container restarts | Alternatives considered: Homebrew PostgreSQL (rejected: machine-specific setup), Docker Compose (deferred: Phase 10 introduces it)
[Phase 04] Decision: The application runs on PostgreSQL but the test suite stays on H2 | Reason: `./mvnw clean verify` must pass on a clean machine with nothing running, and Phase 7 exists precisely to move the tests onto real PostgreSQL with Testcontainers | Alternatives considered: pointing the tests at the same local server (rejected: makes the build depend on a running container three phases early)
[Phase 04] Decision: The `test` profile is activated by surefire's `<systemPropertyVariables>`, not by a `src/test/resources/application.properties` | Reason: an `application.properties` on the test classpath SHADOWS the main one rather than adding to it, so every shared setting in it would be silently lost | Alternatives considered: `@ActiveProfiles("test")` on each test (rejected: easy to forget on a new test), a test-classpath application.properties (rejected: shadowing)
[Phase 04] Decision: Connection details are `${POSTGRES_*:default}` placeholders with throwaway local defaults committed to Git | Reason: the same jar runs anywhere with only environment changes, and a real password arrives as `POSTGRES_PASSWORD` and is never written to a file | Alternatives considered: hard-coded credentials (rejected: cannot be deployed), no defaults (rejected: `./mvnw spring-boot:run` would need a wrapper script)
[Phase 04] Decision: `data.sql` is guarded by `WHERE NOT EXISTS (SELECT 1 FROM product)` as a single statement | Reason: `spring.sql.init.mode=always` re-runs it on every start, and against a database that keeps its rows an unguarded INSERT would add ten more products per restart; one statement means the guard is evaluated once, so it is all ten rows or none | Alternatives considered: `mode=never` after the first run (rejected: manual step, and a fresh database would start empty), one guard per row (rejected: the first insert makes the table non-empty and skips the other nine)
[Phase 04] Decision: H2 runs with `MODE=PostgreSQL` in the test profile | Reason: narrows the dialect gap between what the tests prove and what production runs, at no cost | Alternatives considered: plain H2 (rejected: a wider gap for free)
[Phase 04] Decision: The persistence check spans two smoke-test runs via a `.smoke-state` file | Reason: one run cannot restart the application it is talking to, so the only honest way to prove data outlives the process is to leave a probe behind and look for it after a restart | Alternatives considered: the script restarting the app itself (rejected: it does not own the process), querying PostgreSQL directly with `docker exec` (rejected: couples the script to Docker and a container name)
[Phase 04] Decision: `ddl-auto` stays `update` and the H2 console is removed | Reason: the phase's scope says to keep schema generation until Flyway arrives in Phase 5; the console only ever browsed the in-memory database, and DBeaver, pgAdmin or `psql` replace it | Alternatives considered: `validate` (rejected: there are no migrations yet to validate against)
[Phase 05] Decision: `spring-boot-starter-flyway`, not a bare `org.flywaydb:flyway-core` | Reason: Spring Boot 4 splits auto-configuration into a module per technology, so `flyway-core` alone puts the engine on the classpath with nothing to wire it up — the migrations are silently never run and the application starts against whatever schema it finds | Alternatives considered: `flyway-core` + `spring-boot-flyway` (equivalent, but the starter is the documented entry point), a `FlywayMigrationStrategy` bean (rejected: solves a different problem)
[Phase 05] Decision: V1 reproduces the Phase 4 schema exactly, but with readable constraint names and explicit `ON DELETE` rules | Reason: `ddl-auto=validate` compares tables, columns, types and nullability on every start, so V1 has to match the entities; Hibernate's validator ignores constraint names, foreign keys and indexes, which makes `fk_cart_item_cart` and `ON DELETE CASCADE` free improvements | Alternatives considered: copying `pg_dump` output verbatim (rejected: keeps Hibernate's generated constraint names for ever), hand-writing a different schema (rejected: startup validation would fail)
[Phase 05] Decision: The catalogue seed becomes versioned migration V2, and its `WHERE NOT EXISTS` guard is dropped | Reason: Flyway records that version 2 has been applied and never runs it again, so the idempotency guard Phase 4 needed for `spring.sql.init.mode=always` has nothing left to protect against | Alternatives considered: keeping `data.sql` alongside Flyway (rejected: two mechanisms seeding the same table), a repeatable `R__seed.sql` (rejected: re-runs whenever its checksum changes, which is wrong for rows)
[Phase 05] Decision: V3's `category` column is nullable rather than `NOT NULL DEFAULT` | Reason: expand/contract — during a rolling deploy the migrated schema is live while old instances are still inserting products with no knowledge of the column, and a `NOT NULL` column without a default fails every one of those inserts; tightening it is a later migration's job once every instance writes it | Alternatives considered: `NOT NULL DEFAULT 'UNCATEGORIZED'` (rejected: hides missing data behind a real-looking value), making it required in `ProductRequest` (rejected: breaks existing clients)
[Phase 05] Decision: The test suite runs the same migrations on H2 (`MODE=PostgreSQL`) with `ddl-auto=validate` | Reason: it makes `./mvnw clean verify` fail the moment a migration and the entities drift apart, instead of the next deploy failing to start; it costs nothing and needs no database installed | Alternatives considered: `spring.flyway.enabled=false` for tests with `create-drop` (rejected: the migrations would never be exercised by the build), Testcontainers (deferred: that is Phase 7)
[Phase 05] Decision: The two `@DataJpaTest` repository slices keep `ddl-auto=create-drop` and no Flyway | Reason: `@DataJpaTest` hands each slice its own throwaway database and does not include Flyway's auto-configuration, and these tests are written to own the exact rows they assert on — V2 would seed ten products they never asked for | Alternatives considered: importing `FlywayAutoConfiguration` into the slices (rejected: seed rows leak into query tests), `@AutoConfigureTestDatabase(replace = NONE)` (rejected: the slices would share one database)
[Phase 05] Decision: `baseline-on-migrate=false`, and the Phase 4 database was dropped and rebuilt | Reason: baselining would write a history row for a schema nobody verified and skip straight to the newest migration, so a database built by `ddl-auto=update` would silently differ from one built by V1–V3; on a learning project the data is disposable and a clean rebuild proves the "Done when" outright | Alternatives considered: `baseline-on-migrate=true` (rejected: unverified schema), a `V0__baseline.sql` (rejected: same problem, more files)
[Phase 05] Decision: The smoke test reports a check it could not run as SKIP, counted separately | Reason: the `flyway_schema_history` checks need SQL rather than HTTP, so they depend on a `psql` on PATH or in the container; the testing protocol's honesty rule forbids reporting a check as passed when it never ran | Alternatives considered: passing when psql is missing (rejected: dishonest), failing when psql is missing (rejected: makes the script unusable without Docker), exposing the history over HTTP (rejected: a debug endpoint just for the test)
