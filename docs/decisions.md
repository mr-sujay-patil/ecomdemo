# Decision Log

> One or two lines per decision. Newest at the bottom. Format:
> `[Phase XX] Decision: … | Reason: … | Alternatives considered: …`

[Phase 00] Decision: Merge commits only, no branch deletion | Reason: preserves full phase history and enables ancestry-based merge verification | Alternatives considered: squash merge (rejected: breaks verification)
[Phase 00] Decision: Per-phase docs with a checkpoint file | Reason: keeps each Claude Code session's context small and resumable | Alternatives considered: single roadmap file
[Phase 00] Decision: Repository is public and named `ecomdemo`; the earlier attempt was renamed to `EcomDemo-archive` | Reason: GitHub repo names are case-insensitive, so the old `EcomDemo` blocked the name | Alternatives considered: reusing the old repo (rejected: its `main` already holds ~22 phases of divergent work)
[Phase 00] Decision: Branch protection on `main` with `enforce_admins: true` | Reason: without it GitHub exempts the owner, so "a direct push to main is rejected" would be false for the only person who pushes | Alternatives considered: protection without admin enforcement
[Phase 01] Decision: Spring Boot 4.1.1 on Java 21 | Reason: latest stable 4.x on start.spring.io at the time; Java 21 is the stack's LTS baseline even though JDK 25 is installed locally | Alternatives considered: Boot 4.2.0-M1 (rejected: not GA)
[Phase 01] Decision: Order lines snapshot product name and price, and the order stores its total | Reason: an order is a historical record and must survive repricing or deletion of a product | Alternatives considered: a @ManyToOne to Product with the total derived on read (rejected: rewrites history)
[Phase 01] Decision: The cart total is always derived, never stored | Reason: a stored total is a second source of truth that goes stale when a price or quantity changes | Alternatives considered: a cached total column
[Phase 01] Decision: Lazy associations plus explicit JOIN FETCH queries, and cart writes re-read before mapping | Reason: `save()` on a detached entity merges and returns a copy whose lazy associations are uninitialised proxies, which threw LazyInitializationException; the alternative fix, `@Transactional`, is Phase 6's scope | Alternatives considered: EAGER fetching (rejected: N+1 on every read), @Transactional (deferred to Phase 6)
[Phase 01] Decision: Checkout validates stock for all lines before writing any, but is not yet atomic | Reason: keeps the common failure clean without pulling Phase 6's transaction work forward; the remaining race is the reason Phase 6 exists | Alternatives considered: adding @Transactional now (rejected: out of phase scope)
[Phase 01] Decision: Orders map to table `orders` | Reason: ORDER is a reserved SQL word and an unquoted `insert into order` is a syntax error | Alternatives considered: quoting the identifier everywhere
[Phase 02] Decision: Test at four levels — Mockito unit tests, `@WebMvcTest`, `@DataJpaTest`, and the Phase 1 `@SpringBootTest` | Reason: each slice loads only what it tests, so a failure names its own layer and the suite stays fast (79 tests in ~9s) | Alternatives considered: `@SpringBootTest` everywhere (rejected: slow, and a failure could come from any layer)
[Phase 02] Decision: `MockMvcTester` rather than classic `MockMvc` + Hamcrest matchers | Reason: it is the AssertJ-native MockMvc API in Spring Framework 7, so every assertion in the project reads the same way | Alternatives considered: `mockMvc.perform(...).andExpect(status().isOk())` (rejected: a second assertion vocabulary to learn)
[Phase 02] Decision: Web tests assert the JSON body, not a deserialised DTO | Reason: `BigDecimal.equals()` compares scale as well as value, so a price serialised as 8999.00 and read back as 8999.0 fails an equality check that has nothing to do with the endpoint; JSONAssert compares numbers by value | Alternatives considered: comparing records (rejected: brittle for money), custom comparators (rejected: hides the wire format)
[Phase 02] Decision: `@DataJpaTest` covers only the hand-written `@Query` methods | Reason: everything else on `JpaRepository` is Spring Data's code, and testing a framework's own `findById` adds maintenance without adding confidence | Alternatives considered: testing every repository method
[Phase 02] Decision: Repository tests run with `spring.sql.init.mode=never` | Reason: a repository test should own the rows it asserts on; inheriting `data.sql` would couple the tests to the seed catalogue and break them whenever it changes | Alternatives considered: asserting against the seeded 10 products
[Phase 02] Decision: Generated ids are set reflectively in `TestData` | Reason: several rules key off a product id, and adding `setId()` to the entities purely for tests would let production code invent ids | Alternatives considered: a test-only setter (rejected: weakens the model), mocking the entities (rejected: hides real behaviour like `reduceStock`)
[Phase 02] Decision: Surefire loads the Mockito agent with `-javaagent` | Reason: Mockito self-attaches its bytecode agent today with a warning, and a future JDK will refuse dynamic attachment outright, which would fail the whole unit suite | Alternatives considered: suppressing the warning (rejected: postpones a breakage)
[Phase 03] Decision: springdoc-openapi 3.1.1 | Reason: first GA line built against Spring Boot 4 / Spring Framework 7 (its parent pom builds on Boot 4.1.0); the 2.x line targets Boot 3 | Alternatives considered: springdoc 2.8.x (rejected: wrong Boot generation), hand-written OpenAPI YAML (rejected: drifts from the code)
[Phase 03] Decision: Code-first — the spec is generated from the controllers and DTOs | Reason: one codebase and one author, so a generated document can never disagree with the code it describes | Alternatives considered: contract-first with generated stubs (rejected: its payoff is several teams agreeing on an API before writing code)
[Phase 03] Decision: Document metadata lives in an `OpenAPI` bean (`OpenApiConfig`), not `@OpenAPIDefinition` | Reason: the values are ordinary Java and can later come from configuration or the build, e.g. the version from a release tag | Alternatives considered: the annotation on the application class (rejected: constants only)
[Phase 03] Decision: `@Schema` carries descriptions and examples only; validation rules are not restated | Reason: springdoc already derives `required`, `maxLength` and `minimum` from the Bean Validation annotations, and restating them creates two sources of truth that can disagree | Alternatives considered: spelling out every constraint in `@Schema`
[Phase 03] Decision: Every `@Content` on an error response names `mediaType = "application/json"` | Reason: `@Content` with only a schema documents the body as `*/*`, while `GlobalExceptionHandler` actually returns JSON; the smoke check caught the mismatch | Alternatives considered: leaving the default (rejected: the document would be wrong)
[Phase 03] Decision: The spec is guarded by an automated test as well as the smoke script | Reason: `OpenApiDocumentationTest` fails the build when a controller is added without annotations, instead of waiting for someone to run the smoke test against a live app | Alternatives considered: smoke checks only (rejected: not run by `verify`, and CI arrives in Phase 11)
[Phase 03] Decision: `/v3/api-docs` and Swagger UI stay enabled, accepting springdoc's two startup WARNs | Reason: an explorable API is the point of the phase and there is no production profile yet; springdoc only warns that an open spec reveals the API's shape | Alternatives considered: disabling them (rejected: defeats the phase), a profile switch (deferred: Phase 8 decides access)
[Phase 04] Decision: PostgreSQL 18 from the official `postgres:18-alpine` image, started with one `docker run` | Reason: no installation to undo, the same image the later Docker Compose and Kubernetes phases will use, and the data lives in a Docker volume so it survives container restarts | Alternatives considered: Homebrew PostgreSQL (rejected: machine-specific setup), Docker Compose (deferred: Phase 10 introduces it)
[Phase 04] Decision: The application runs on PostgreSQL but the test suite stays on H2 | Reason: `./mvnw clean verify` must pass on a clean machine with nothing running, and Phase 7 exists precisely to move the tests onto real PostgreSQL with Testcontainers | Alternatives considered: pointing the tests at the same local server (rejected: makes the build depend on a running container three phases early)
[Phase 04] Decision: The `test` profile is activated by surefire's `<systemPropertyVariables>`, not by a `src/test/resources/application.properties` | Reason: an `application.properties` on the test classpath SHADOWS the main one rather than adding to it, so every shared setting in it would be silently lost | Alternatives considered: `@ActiveProfiles("test")` on each test (rejected: easy to forget on a new test), a test-classpath application.properties (rejected: shadowing)
[Phase 04] Decision: Connection details are `${POSTGRES_*:default}` placeholders with throwaway local defaults committed to Git | Reason: the same jar runs anywhere with only environment changes, and a real password arrives as `POSTGRES_PASSWORD` and is never written to a file | Alternatives considered: hard-coded credentials (rejected: cannot be deployed), no defaults (rejected: `./mvnw spring-boot:run` would need a wrapper script)
[Phase 04] Decision: `data.sql` is guarded by `WHERE NOT EXISTS (SELECT 1 FROM product)` as a single statement | Reason: `spring.sql.init.mode=always` re-runs it on every start, and against a database that keeps its rows an unguarded INSERT would add ten more products per restart; one statement means the guard is evaluated once, so it is all ten rows or none | Alternatives considered: `mode=never` after the first run (rejected: manual step, and a fresh database would start empty), one guard per row (rejected: the first insert makes the table non-empty and skips the other nine)
[Phase 04] Decision: H2 runs with `MODE=PostgreSQL` in the test profile | Reason: narrows the dialect gap between what the tests prove and what production runs, at no cost | Alternatives considered: plain H2 (rejected: a wider gap for free)
[Phase 04] Decision: The persistence check spans two smoke-test runs via a `.smoke-state` file | Reason: one run cannot restart the application it is talking to, so the only honest way to prove data outlives the process is to leave a probe behind and look for it after a restart | Alternatives considered: the script restarting the app itself (rejected: it does not own the process), querying PostgreSQL directly with `docker exec` (rejected: couples the script to Docker and a container name)
[Phase 04] Decision: `ddl-auto` stays `update` and the H2 console is removed | Reason: the phase's scope says to keep schema generation until Flyway arrives in Phase 5; the console only ever browsed the in-memory database, and DBeaver, pgAdmin or `psql` replace it | Alternatives considered: `validate` (rejected: there are no migrations yet to validate against)
[Phase 05] Decision: `spring-boot-starter-flyway`, not a bare `org.flywaydb:flyway-core` | Reason: Spring Boot 4 splits auto-configuration into a module per technology, so `flyway-core` alone puts the engine on the classpath with nothing to wire it up — the migrations are silently never run and the application starts against whatever schema it finds | Alternatives considered: `flyway-core` + `spring-boot-flyway` (equivalent, but the starter is the documented entry point), a `FlywayMigrationStrategy` bean (rejected: solves a different problem)
[Phase 05] Decision: V1 reproduces the Phase 4 schema exactly, but with readable constraint names and explicit `ON DELETE` rules | Reason: `ddl-auto=validate` compares tables, columns, types and nullability on every start, so V1 has to match the entities; Hibernate's validator ignores constraint names, foreign keys and indexes, which makes `fk_cart_item_cart` and `ON DELETE CASCADE` free improvements | Alternatives considered: copying `pg_dump` output verbatim (rejected: keeps Hibernate's generated constraint names for ever), hand-writing a different schema (rejected: startup validation would fail)
[Phase 05] Decision: The catalogue seed becomes versioned migration V2, and its `WHERE NOT EXISTS` guard is dropped | Reason: Flyway records that version 2 has been applied and never runs it again, so the idempotency guard Phase 4 needed for `spring.sql.init.mode=always` has nothing left to protect against | Alternatives considered: keeping `data.sql` alongside Flyway (rejected: two mechanisms seeding the same table), a repeatable `R__seed.sql` (rejected: re-runs whenever its checksum changes, which is wrong for rows)
[Phase 05] Decision: V3's `category` column is nullable rather than `NOT NULL DEFAULT` | Reason: expand/contract — during a rolling deploy the migrated schema is live while old instances are still inserting products with no knowledge of the column, and a `NOT NULL` column without a default fails every one of those inserts; tightening it is a later migration's job once every instance writes it | Alternatives considered: `NOT NULL DEFAULT 'UNCATEGORIZED'` (rejected: hides missing data behind a real-looking value), making it required in `ProductRequest` (rejected: breaks existing clients)
[Phase 05] Decision: The test suite runs the same migrations on H2 (`MODE=PostgreSQL`) with `ddl-auto=validate` | Reason: it makes `./mvnw clean verify` fail the moment a migration and the entities drift apart, instead of the next deploy failing to start; it costs nothing and needs no database installed | Alternatives considered: `spring.flyway.enabled=false` for tests with `create-drop` (rejected: the migrations would never be exercised by the build), Testcontainers (deferred: that is Phase 7)
[Phase 05] Decision: The two `@DataJpaTest` repository slices keep `ddl-auto=create-drop` and no Flyway | Reason: `@DataJpaTest` hands each slice its own throwaway database and does not include Flyway's auto-configuration, and these tests are written to own the exact rows they assert on — V2 would seed ten products they never asked for | Alternatives considered: importing `FlywayAutoConfiguration` into the slices (rejected: seed rows leak into query tests), `@AutoConfigureTestDatabase(replace = NONE)` (rejected: the slices would share one database)
[Phase 05] Decision: `baseline-on-migrate=false`, and the Phase 4 database was dropped and rebuilt | Reason: baselining would write a history row for a schema nobody verified and skip straight to the newest migration, so a database built by `ddl-auto=update` would silently differ from one built by V1–V3; on a learning project the data is disposable and a clean rebuild proves the "Done when" outright | Alternatives considered: `baseline-on-migrate=true` (rejected: unverified schema), a `V0__baseline.sql` (rejected: same problem, more files)
[Phase 05] Decision: The smoke test reports a check it could not run as SKIP, counted separately | Reason: the `flyway_schema_history` checks need SQL rather than HTTP, so they depend on a `psql` on PATH or in the container; the testing protocol's honesty rule forbids reporting a check as passed when it never ran | Alternatives considered: passing when psql is missing (rejected: dishonest), failing when psql is missing (rejected: makes the script unusable without Docker), exposing the history over HTTP (rejected: a debug endpoint just for the test)
[Phase 06] Decision: The retry loop (`OrderService.place`) and the transactional unit of work (`OrderPlacementService.placeOnce`) are separate beans | Reason: `@Transactional` is applied by a proxy, so a call from one method of a class to another of the same class never crosses it — a self-invoked `placeOnce()` would run with no transaction at all while looking correct; retrying also *needs* a fresh transaction each attempt, because a failed flush leaves the persistence context unusable and the transaction rollback-only | Alternatives considered: both methods on `OrderService` (rejected: the self-invocation pitfall, silently), injecting the bean into itself (rejected: works, but obscures why), Spring Retry's `@Retryable` (rejected: a second proxy to explain in a phase already about proxies)
[Phase 06] Decision: Optimistic locking (`@Version` on `Product`), not pessimistic | Reason: no lock is taken and no transaction waits; the conflict is detected at write time by `UPDATE ... WHERE id = ? AND version = ?` affecting zero rows, and the loser retries. That is the right trade for a catalogue browsed far more often than it is sold from | Alternatives considered: `SELECT ... FOR UPDATE` (rejected: serialises every checkout of a popular product behind one row lock), SERIALIZABLE isolation (rejected: prevents the same anomaly at far greater cost), a database-level `CHECK (stock_quantity >= 0)` (rejected: turns a business conflict into a constraint violation with no useful message)
[Phase 06] Decision: `order_audit` has no foreign key to `orders`, and `order_id` is nullable | Reason: the row is written with `REQUIRES_NEW`, so it commits while the order's own INSERT is still uncommitted and invisible to it — a foreign key would fail; a REJECTED attempt has no order at all. An audit trail is a log, not a relation: it must be able to outlive and disagree with what it describes | Alternatives considered: a `@ManyToOne` to `Order` (rejected: cannot be satisfied from a separate transaction), writing the audit in the same transaction (rejected: the rejection rolls back with everything else, losing exactly the record worth keeping)
[Phase 06] Decision: The per-line stock pre-check stays, even though the transaction would undo a partial reduction | Reason: failing before any write produces the accurate "requested 3, available 2" message naming the line that is actually short, rather than whichever one happened to break first, and saves the database work it would only throw away | Alternatives considered: deleting it and relying on rollback (rejected: worse errors for no gain), checking only at write time (rejected: same)
[Phase 06] Decision: `CartService` is read-write throughout, `view()` included | Reason: the single shared cart row is created on first use, so even the "read" can insert; `readOnly = true` puts Hibernate into manual flush mode and that insert would be prepared and silently dropped | Alternatives considered: `readOnly` on `view()` with `currentCart()` overriding it (rejected: `view()` calls it internally — self-invocation again, so the outer read-only transaction would be the one in force), returning a transient cart for viewing (rejected: changes behaviour to suit an annotation)
[Phase 06] Decision: `ProductService` declares `@Transactional(readOnly = true)` at class level, with the four writing methods overriding it | Reason: a new read method is then safe by default and a new write method fails loudly if its author forgets to annotate it, rather than the other way round | Alternatives considered: annotating each read (rejected: a forgotten write is the dangerous direction), no class-level default (rejected: same)
[Phase 06] Decision: Three attempts, then `ConcurrentUpdateException` → HTTP 409 | Reason: a retry only helps when the conflict was momentary; three absorbs the one-off collision optimistic locking is designed for and gives up quickly on a stampede, and an exhausted budget is a conflict with current state (409), not a server error (500) — the client can reasonably repeat the request | Alternatives considered: retrying indefinitely (rejected: holds connections while the client waits), no retry (rejected: a single unlucky collision would be a visible failure), 503 + `Retry-After` (rejected: nothing is unavailable)
[Phase 06] Decision: The smoke test fires its two racing checkouts from one `curl` with `--parallel --parallel-immediate` | Reason: two backgrounded `curl` processes each pay ~10 ms of start-up against a ~5 ms checkout, so the second usually arrived after the first had committed — the check passed for the wrong reason and would have kept passing with the locking removed; inside one process the requests genuinely overlap and the versioned UPDATE is rejected on every run | Alternatives considered: two background curls (rejected: does not reliably race), `ab`/`hey` (rejected: another tool to install for two requests)
[Phase 07] Decision: H2 stays; the integration tests are a second suite rather than a replacement | Reason: the two suites answer different questions — "is the Java right?" (120 tests, 9 s, no Docker, run constantly) and "is this true of PostgreSQL?" (15 tests, a container start, run before pushing); deleting H2 would buy honesty in the fast suite at the price of making every inner-loop run need Docker, which is the trade the test pyramid exists to avoid | Alternatives considered: moving the whole suite onto Testcontainers (rejected: slows the loop developers run fifty times a day, and most of those tests never touch SQL), keeping H2 only for the `@DataJpaTest` slices (rejected: an arbitrary line — the `@SpringBootTest` classes are equally about Java, not SQL)
[Phase 07] Decision: The container is a Spring `@Bean` annotated `@ServiceConnection`, not `@Container` with `@DynamicPropertySource` | Reason: Spring then owns the lifecycle (start with the context, stop when it closes) and derives the JDBC url, username and password from the container itself, so no connection string is written in any test and there is no chance of a stale one pointing at a developer's own database | Alternatives considered: Testcontainers' JUnit extension plus `@DynamicPropertySource` (rejected: the test has to copy the random port by hand, and the container's lifetime no longer matches the context's), the JDBC url scheme `jdbc:tc:postgresql:///` (rejected: hides the container in a string, and cannot be configured further)
[Phase 07] Decision: One shared context for every `*IT`, via a single `IntegrationTest` base class | Reason: Spring caches an application context by the annotations that define it, so keeping all of them in one place is what makes the three IT classes share one context and therefore one container — the first class pays ~12 s, the others ~0.1 s; scattering the annotations would silently buy a container per class | Alternatives considered: annotating each IT separately (rejected: one differing annotation is one extra container, with no error to say so), a static container started in a `@BeforeAll` (rejected: hand-rolls what the context cache already does)
[Phase 07] Decision: `withReuse(true)` is deliberately not enabled | Reason: it leaves the container running between builds, and with it the previous run's rows — a build that passes because of yesterday's data is worse than a build that spends another six seconds; the two lines that enable it are documented in `PostgresContainerConfig` for anyone who wants the faster loop | Alternatives considered: enabling reuse (rejected: cross-run state), truncating every table before each class (rejected: reintroduces the cleanup problem reuse was meant to avoid)
[Phase 07] Decision: Failsafe is bound to both `integration-test` and `verify`, not `integration-test` alone | Reason: `integration-test` records a failure but does not stop the build, so that `post-integration-test` always runs and tears down what the tests started; the `verify` goal is what reads those results and fails the build. With only the first goal bound, a failing IT is silently green — this was confirmed with a throwaway failing test | Alternatives considered: binding only `integration-test` (rejected: proven not to fail the build), running the ITs under Surefire by renaming them `*Test` (rejected: `./mvnw test` would then need Docker)
[Phase 07] Decision: The image tag is pinned to `postgres:18-alpine`, matching the dev profile | Reason: an integration test is a claim about a specific engine version; `latest` would make the claim depend on what Docker Hub published that morning, and a version drift between the test database and the dev database defeats the purpose of running the test at all | Alternatives considered: `postgres:latest` (rejected: irreproducible), a digest pin (rejected: unreadable for a learning project, and the tag is already specific)
[Phase 08] Decision: Two migrations — V5 adds `users` and the seeded admin, V6 attaches the cart and the orders to it | Reason: they answer different questions and either could be wanted without the other; splitting them also keeps each file small enough to read as one idea, and V6's three-step `NOT NULL` dance is easier to follow without the table creation above it | Alternatives considered: one V5 doing everything (rejected: two unrelated concerns, and an applied migration can never be split afterwards)
[Phase 08] Decision: The first ADMIN is seeded by a migration, and registration always creates a CUSTOMER | Reason: an anonymous endpoint that accepts a role hands out administrator accounts to whoever asks — the classic privilege-escalation hole; the first admin therefore has to come from something that already has database access | Alternatives considered: a `role` field on `RegisterRequest` (rejected: the hole itself), a bootstrap endpoint that works only while `users` is empty (rejected: a race and a permanent extra endpoint), an env-var-driven `CommandLineRunner` (rejected: puts account creation outside the migration history)
[Phase 08] Decision: The seeded admin's BCrypt hash is written literally into V5, and the password (`admin123`) is documented in the README | Reason: PostgreSQL can hash with pgcrypto and H2 cannot, so a computed hash would make the migration untestable by the fast suite; the credential is a throwaway local development value in the same spirit as the `ecomdemo/ecomdemo` database password already in Git, and the README says plainly that a real deployment changes it first | Alternatives considered: a Flyway placeholder fed from an env var (rejected: the fast suite and the ITs would then need it set too), `pgcrypto` (rejected: PostgreSQL-only, breaks the H2 suite), leaving no admin at all (rejected: nothing could then create a product)
[Phase 08] Decision: ADMIN is refused (403) on `/api/cart/**` and `/api/orders/**` | Reason: those endpoints act on "my" cart and "my" orders, and an administrator has neither; nothing about being an admin implies being a customer, and quietly granting both is how a role system stops meaning anything. It is also the phase file's wording taken literally: "cart and orders require CUSTOMER" | Alternatives considered: `hasAnyRole("CUSTOMER","ADMIN")` (rejected: an admin would silently get a cart), a role hierarchy with ADMIN > CUSTOMER (rejected: implies an admin is a superset of a customer, which is false for ownership-scoped data)
[Phase 08] Decision: Reading another account's order is 403 (`@PostAuthorize`), not 404 | Reason: the phase file allows either; 403 says plainly "that is not yours", where a 404 makes a client think its own order has vanished. It does admit the order exists, which for order ids already visible to their owner is an acceptable trade — for something like a private document it would not be | Alternatives considered: filtering by `user_id` in the query so a stranger's id is a 404 (rejected here, but it is the right default for more sensitive resources — noted in `OrderService.findById`)
[Phase 08] Decision: `@PreAuthorize` for the role, `@PostAuthorize` for ownership | Reason: the rule "this order must belong to the caller" cannot be evaluated before the call, because whose order it is, is in the row; `@PostAuthorize` runs after with the return value bound to `returnObject`. The cost is that the work is already done when the answer is no, so it belongs only on reads — on a write the transaction would roll back but side effects outside it (a log line, an email, a queue message) would not | Alternatives considered: loading the order in the controller and checking by hand (rejected: the check then has to be remembered at every call site), a custom `PermissionEvaluator` (rejected: heavy machinery for one rule)
[Phase 08] Decision: "Only your own orders" is enforced by the query (`findAllByUserIdWithItems`), not by filtering a full result | Reason: filtering after the fact means the method has already read rows the caller may not see, and is one forgotten `filter` away from returning them; putting the owner in the `where` clause means they never leave the database. The repository deliberately has no "load every order" method at all | Alternatives considered: `findAll()` plus a stream filter (rejected: reads other people's data), a Hibernate `@Filter` (rejected: global state that is easy to forget to enable)
[Phase 08] Decision: CSRF protection is disabled | Reason: CSRF attacks ambient authority — a cookie the browser attaches by itself. This API is stateless (`SessionCreationPolicy.STATELESS`), sets no cookie and reads credentials from an `Authorization` header the client must attach deliberately, so a cross-site form arrives with no credentials and is answered 401. The token would protect nothing and break every non-browser client. This reasoning depends on statelessness and must be revisited if cookies ever appear | Alternatives considered: leaving it on (rejected: breaks curl, Swagger "Try it out" and every future service client for no gain), `CookieCsrfTokenRepository` (rejected: same, plus a cookie)
[Phase 08] Decision: 401 and 403 are written by an `AuthenticationEntryPoint` and an `AccessDeniedHandler`, not by `GlobalExceptionHandler` | Reason: a request the security filter chain rejects never reaches the `DispatcherServlet`, so there is no controller, no handler method and no `@RestControllerAdvice` to run — only a `HttpServletResponse` somebody has to fill in. The advice does still handle `AccessDeniedException` for method-security denials, which happen after a controller has been entered | Alternatives considered: relying on the advice alone (rejected: never invoked for URL-level denials), letting Spring Security's empty-body defaults stand (rejected: two statuses with a different contract from every other error)
[Phase 08] Decision: No `WWW-Authenticate` header on a 401 | Reason: it is correct HTTP and it makes a browser pop up its native login dialog — unstyleable, uncancellable and impossible to log out of. The clients here are curl, Swagger UI and the smoke test, none of which need it | Alternatives considered: Spring Security's default `WWW-Authenticate: Basic realm="Realm"` (rejected: the browser dialog)
[Phase 08] Decision: A JPA `User` entity and a separate `AppUserDetails` adapter, rather than making the entity implement `UserDetails` | Reason: the persistence model stays free of framework interfaces and Spring Security stays free of JPA, so either side can change without dragging the other along; the adapter is also where the `ROLE_` prefix is added, keeping that Spring convention out of the database. It additionally carries the account id, which the cart and the orders are keyed by | Alternatives considered: `class User implements UserDetails` (rejected: couples the schema to a framework interface and tempts `getPassword()` into DTOs)
[Phase 08] Decision: `CurrentUser` is an injected bean wrapping `SecurityContextHolder`, not a static call | Reason: services that need "who is calling" stay unit-testable — a test stubs a collaborator instead of populating a thread-local and tearing it down; it also puts the "no authenticated user on this thread" failure in one place, where it can explain itself | Alternatives considered: `SecurityContextHolder.getContext()` inline in each service (rejected: static state in every test), an `@AuthenticationPrincipal` controller parameter threaded down (rejected: every signature grows a parameter that is not part of the domain)
[Phase 08] Decision: `support/WithSecurityRules` imports the real `SecurityConfig` into every `@WebMvcTest` | Reason: `@WebMvcTest` auto-configures Spring Security but does **not** pick up the application's own `SecurityFilterChain` — a slice scans web components and a `@Configuration` class is not one — so the slice silently runs against Boot's fallback "authenticate everything" chain. A test asserting "anonymous gets 401" then passes while proving nothing about the rules that were written | Alternatives considered: repeating a five-class `@Import` in each slice (rejected: noise, and a different import set means a different context cache key and a second context), trusting the fallback chain (rejected: tests the framework's default, not our rules)
[Phase 08] Decision: `@SpringBootTest` classes authenticate as a persisted account via `support/TestAuthentication`, not `@WithMockUser` | Reason: `@WithMockUser` installs a Spring Security `User` principal, but `CurrentUser` needs an `AppUserDetails` carrying the database id — and a fabricated principal names an account that does not exist, so the first `currentUser.require()` fails. Signing in as a row actually in the database keeps the principal, the `users` row and the cart's `user_id` genuinely in agreement | Alternatives considered: `@WithUserDetails` (rejected: still needs the row to exist, and hides where it came from), loosening `CurrentUser` to accept any principal (rejected: weakens production code to suit a test)
[Phase 08] Decision: `ApiErrorWriter` injects Jackson 3's `tools.jackson.databind.json.JsonMapper` | Reason: Spring Boot 4 auto-configures Jackson 3 and defines **no** `com.fasterxml.jackson.databind.ObjectMapper` bean, even though Jackson 2 is still on the classpath via other libraries; injecting the Jackson 2 type fails context startup, and using it manually would format these two responses with a different mapper from every other response | Alternatives considered: `new ObjectMapper()` inside the class (rejected: diverges from the application's configured mapper), hand-writing the JSON string (rejected: an error shape that escapes the type system)
[Phase 08] Decision: V6 deletes the existing cart rows but keeps existing orders, attributing them to the seeded admin | Reason: a cart is scratch state — a few minutes of browsing — and there is no correct account to attribute one assembled by "everyone" to; an order is a financial record and deleting it would throw away the very history the table exists for. [Phase 09] Decision: A `JWT_SECRET` shorter than 32 bytes fails startup rather than being padded or hashed up to length | Reason: HS256 is HMAC-SHA256 and needs a 256-bit key; quietly stretching a short secret leaves an application running with a weaker signature than its configuration implies, and nothing ever says so | Alternatives considered: SHA-256 the secret to length (rejected: hides a weak input behind a strong-looking key), letting Nimbus fail with its own message (rejected: says nothing about what to do)
[Phase 09] Decision: HS256 (symmetric), not RS256 | Reason: one application both issues and accepts these tokens, so one secret is enough and there is no key distribution to arrange. The trade is written down because it expires: the moment a second service must accept these tokens, giving it the key to verify also gives it the power to issue, and that is the point to move to RS256 with a published public key | Alternatives considered: RS256 with a generated keypair (rejected: key management and a JWKS endpoint are a phase of their own, and nothing yet needs them), an opaque token with server-side lookup (rejected: that is a session, which is the thing this phase exists to contrast with)

[Phase 09] Decision: The `uid` claim is read as `Number` and narrowed, not cast to `Long` | Reason: JSON has one number type, so a claim written as a `Long` comes back as an `Integer` for small values and a `Long` for large ones — a direct cast works until the users table passes two billion rows, which is the worst kind of bug to ship | Alternatives considered: `getClaim(...)` with a `Long` type parameter (rejected: same ClassCastException, later), writing the id as a string claim (rejected: a number that is not a number)

[Phase 09] Decision: Expired-token tests mint a token whose whole lifetime is two hours in the past, rather than using a very short expiry and waiting | Reason: the decoder allows 60 seconds of clock skew, so a "1 second" token is still accepted for another minute — a waiting test would have to burn that minute and would prove less. A token signed with the real key but long expired isolates the clock from the signature | Alternatives considered: a 1-second expiry plus a sleep (rejected: slow and, because of skew, wrong), shrinking the clock skew (rejected: changes production behaviour to suit a test)
[Phase 09] Decision: The smoke test signs its expired token with `JWT_SECRET` when available and falls back to an unsigned one, saying which path ran | Reason: only a correctly signed token proves that *expiry* caused the 401; an unsigned one is refused for the signature instead. The script cannot know the key unless the operator exports it, so it does the strong check when it can and states plainly when it did the weaker one — the testing protocol's honesty rule | Alternatives considered: always unsigned (rejected: silently tests something else), skipping the check without a key (rejected: the weaker check is still worth running), reading the key out of the running process (rejected: not possible, and would be alarming if it were)
[Phase 09] Decision: `LoginRequest` overrides `toString()` to mask the password | Reason: a record's generated `toString()` prints every component, and a request DTO is exactly the kind of object that ends up in a debug log or an exception message | Alternatives considered: relying on never logging it (rejected: one `log.debug("{}", request)` away from a password in a log file)
[Phase 09] Decision: Two `printf`-built JSON bodies in the smoke test instead of inline escaped quotes | Reason: bash 3.2 — still what macOS ships — mis-splits escaped double quotes nested inside a command substitution inside a quoted string, and the body arrived mangled. Buildpacks are the better default for a team that wants to stop thinking about images — automatic CVE rebases, no Dockerfile to rot — and this project exists to think about them | Alternatives considered: `spring-boot:build-image` (rejected: hides exactly what the phase is about, and 356 MB larger), jib (rejected: same opacity, plus another plugin), a single-stage build (rejected: ships the JDK, Maven and the source to production)
[Phase 10] Decision: Multi-stage, with the JRE-only runtime stage as the published image | Reason: the build stage needs a JDK, Maven and the whole source tree (~556 MB of tooling before any dependency); none of it is needed to run, and shipping a compiler and the source code to production is an avoidable liability. [Phase 10] Decision: The fat jar is exploded with `jarmode=tools extract --layers --launcher`, and copied in four ordered `COPY` steps | Reason: a Spring Boot fat jar is one 64 MB file, so a one-line change rewrites all 64 MB and pushes a whole new layer. Extracting by layer means dependencies (~64 MB) stay cached and only the application layer (~200 KB) is rebuilt and pushed | Alternatives considered: `COPY target/*.jar app.jar` (rejected: 64 MB per push for a one-character change), `-Djarmode=layertools` (rejected: the Boot 2/3 spelling, replaced in Boot 3.3)
[Phase 10] Decision: Dependencies are resolved in their own layer, before the source is copied | Reason: Docker invalidates every layer after the first changed instruction, so copying `pom.xml` and running `dependency:go-offline` first means an ordinary code edit reuses the cached ~200 MB dependency layer. Measured: a rebuild after touching one source file takes 5 s | Alternatives considered: one `COPY . .` (rejected: re-downloads every dependency on every build)
[Phase 10] Decision: The container runs as a fixed non-root uid 1001, created in the image | Reason: a container's root IS the host's root — the isolation is namespaces, not a separate user table — so an escape or a bind mount hands over root for no benefit; this application never installs a package, writes to /etc or binds a port below 1024. The uid is pinned rather than left to the distribution because bind-mounted files are owned by a NUMBER, and a uid that drifts between rebuilds becomes "permission denied" on a mount that worked yesterday | Alternatives considered: running as root (rejected: the default is not a reason), `user:` in compose only (rejected: the image would still be root-by-default for anyone running it directly)
[Phase 10] Decision: `-XX:MaxRAMPercentage=75.0` rather than a fixed `-Xmx`, and a memory limit on the compose service | Reason: a modern JVM reads the container's limit, but defaults the heap to 25% of it — a 768 MB container would run a 192 MB heap and spend its life in GC. A percentage follows the limit wherever the image runs, where an `-Xmx` number is wrong the moment the limit changes. The limit in compose matters too: without one the percentage is 75% of the whole host. 75% and not more, because metaspace, thread stacks, code cache and direct buffers are not heap | Alternatives considered: `-Xmx512m` (rejected: hard-codes an answer to a question the deployment asks), `MinRAMPercentage` (rejected: it only applies below ~250 MB of available memory, which is a trap), no setting at all (rejected: a quarter of the memory used, by default)
[Phase 10] Decision: `-XX:+ExitOnOutOfMemoryError` | Reason: a JVM that has exhausted its heap will not recover, and a container that keeps passing health checks while failing every request is worse than one that dies and is restarted. Restarting is what `restart: unless-stopped` and, later, an orchestrator are for | Alternatives considered: letting it limp (rejected: a half-dead instance keeps receiving traffic), `HeapDumpOnOutOfMemoryError` as well (deferred: a dump needs somewhere to write it, which is a volume decision for a later phase)
[Phase 10] Decision: `depends_on: db: condition: service_healthy`, with `pg_isready` as the health check | Reason: the short `depends_on: [db]` waits only for the container to be STARTED, which for PostgreSQL means "the process exists" — several seconds before it accepts connections. The application then dies at startup with a Flyway connection error, intermittently, which is the worst kind of failure to debug | Alternatives considered: bare `depends_on` (rejected: proven insufficient), a wait-for-it script in the entrypoint (rejected: reimplements what compose already does), relying on `restart: unless-stopped` to retry (rejected: turns a startup ordering bug into a crash loop that usually resolves itself, which teaches nothing)
[Phase 10] Decision: The application reaches PostgreSQL at `db:5432` over the compose network, not at a published host port | Reason: Compose puts both services on one network with DNS, so `db` resolves inside it. Hoisting the argument out makes the assertion mean what it says | Alternatives considered: suppressing the rule in tests (rejected: the ambiguity is real), ignoring it as test-only (rejected: a test that can pass for the wrong reason is worse than no test)
[Phase 12] Decision: `sonar.coverage.exclusions` covers `EcomdemoApplication` and the `dto` packages | Reason: they are excluded from COVERAGE, not from analysis - Sonar still reports bugs and smells in them. [Phase 13] Decision: Only the two catalogue reads are cached; `requireProduct` is deliberately NOT | Reason: it returns the managed JPA entity that the cart and checkout use, and a cached copy would carry a stale `stockQuantity` AND a stale `version`. That is worse than ordinary staleness: optimistic locking could not catch it, because the version it compares would itself have come from the cache — the Phase 6 oversell bug would return in a form the Phase 6 race test could not detect, since both threads would agree on the same wrong number. The rule this phase is really about: cache what is read often and changes rarely; never cache what a decision is made against | Alternatives considered: caching `requireProduct` with a short TTL (rejected: a short window for a lost update is still a lost update), caching the entity and evicting on every checkout (rejected: evicting inside an uncommitted transaction lets a concurrent read repopulate from pre-commit state)
[Phase 13] Decision: DTOs are cached, never entities | Reason: a `ProductResponse` is a snapshot with no Hibernate proxies, no lazy associations and no identity that could be confused with a managed instance. A cached entity is detached the moment it is stored, and handing a detached entity back into a persistence context is how "why is this object not saving" bugs start | Alternatives considered: caching `Product` (rejected: detached entities, lazy-loading failures, and the stock problem above)
[Phase 13] Decision: One JSON serializer per cache, typed to exactly what that cache holds — NOT a generic serializer with Jackson default typing | Reason: two problems, and the first one bit. (1) Default typing did not round-trip: it wrote a root-level `List` as a bare JSON array with no type id, then demanded one on read — `Could not read JSON: Unexpected token (START_OBJECT), expected VALUE_STRING: need ... type id`. Every cached listing read failed, having written something it could not read back. (2) "The document names the class to instantiate" is a deserialization gadget and a well-trodden path to remote code execution; Jackson's own convenience method for it is called `enableUnsafeDefaultTyping`. A per-cache type removes both, produces smaller documents with no `@class`, and forces the question "what does this cache hold?" | Alternatives considered: `GenericJacksonJsonRedisSerializer` with a `BasicPolymorphicTypeValidator` allow-list (tried first; the allow-list fixed the security half and not the round-trip half), the JDK serializer (rejected: unreadable in redis-cli, requires Serializable, and breaks on any class change)
[Phase 13] Decision: A `CacheErrorHandler` logs and falls through instead of rethrowing | Reason: the default rethrows, so anything wrong with Redis — down, slow, or holding an entry an older build wrote — becomes a failed request. That is backwards: a cache-aside cache is an optimisation over a database that can still answer, so losing it should cost latency, not availability. Not hypothetical here — the serializer bug turned every catalogue read into a 500 for a cache the application did not need. Verified by stopping Redis and watching `/api/products` keep returning 200 | Alternatives considered: the default rethrowing handler (rejected: proven to convert a cache bug into an outage), catching in each service (rejected: the same code in five places, and easy to forget in the sixth)
[Phase 13] Decision: Every cache has a TTL — 10 minutes for a product, 2 for the listing | Reason: explicit `@CacheEvict` handles the changes this application makes; the TTL handles everything else — a migration, a manual UPDATE, a bug in an eviction rule, an evict swallowed by the error handler above. Without one, a single missed eviction is wrong for ever. The listing expires faster because it is ONE key covering every product: the most expensive entry to hold and the most likely to be wrong | Alternatives considered: no TTL with eviction alone (rejected: assumes every eviction path is correct for ever), one TTL for both (rejected: the two entries have genuinely different staleness costs)
[Phase 13] [SUPERSEDED by the Phase 16 follow-up below — the hazard was real, the cost was underestimated] Decision: `productService.save` (the checkout write path) evicts nothing | Reason: it is called once per line inside a transaction that may still roll back. Evicting there would discard good entries on every failed checkout, and — worse — evict before the commit, so a concurrent read could repopulate the cache from pre-commit state and be wrong until the TTL. The honest cost is that a cached product shows the old stock figure for up to its TTL after a sale; the catalogue is a browsing view and checkout reads live, so nothing decides on the stale number | Alternatives considered: `@CacheEvict` on save (rejected: the pre-commit repopulation race), `@CacheEvict(beforeInvocation = false)` plus transaction synchronisation (rejected: real, and a phase of its own)
[Phase 13] Decision: `/error` is permitted in the security filter chain | Reason: Spring forwards an unhandled exception to `/error`, and that forward goes through the filter chain like any other dispatch — so `anyRequest().authenticated()` answered it 401. A genuine 500 on a PUBLIC endpoint therefore reached the client as "authentication required", which is a long way in the wrong direction for whoever is debugging it. That is exactly what the serializer bug did, and the 401 hid it. Latent since Phase 8 and only visible once something finally threw | Alternatives considered: `shouldFilterAllDispatcherTypes(false)` (rejected: turns off security for every non-REQUEST dispatch, a bigger change than the problem), leaving it (rejected: every future 500 on a public endpoint would be mislabelled)
[Phase 13] Decision: The Redis container is declared in the shared `IntegrationTest` configuration, beside PostgreSQL | Reason: Spring caches a context by its whole annotation set, so declaring Redis on one test class would give that class a context of its own — and with it a second PostgreSQL as well as a Redis. Confirmed by counting: one `Creating container for image: redis` and one for postgres across the entire Failsafe run. The Phase 7 lesson applied rather than re-learned | Alternatives considered: a container per test class (rejected: pays for a pair of containers per class), a static container outside Spring (rejected: hand-rolls what the context cache already does)
[Phase 13] Decision: `spring.cache.type=none` in the `test` profile | Reason: it keeps the Phase 7 promise that `./mvnw test` needs no Docker — verified, 0 containers and 190 tests. It is not a gap: caching behaviour is a claim about a real cache (a second read skips the database, an update evicts, a BigDecimal survives JSON), and none of it can be proven against a HashMap standing in for Redis. It is proven in `CacheApiIT` against a real one | Alternatives considered: a `ConcurrentMapCacheManager` in tests (rejected: tests the stand-in, not the thing), Redis for the fast suite too (rejected: breaks the Docker-free inner loop)
[Phase 13] Decision: The integration test empties Redis by deleting keys, not by calling `CacheManager.clear()` | Reason: `RedisCache.clear()` logged and returned without error while the keys survived, so a test built on it would "start from an empty cache" without doing so — and would then pass or fail for reasons unrelated to what it checks. The application never calls `clear()`: every eviction it performs names an explicit key, and those are covered directly | Alternatives considered: `CacheManager.clear()` (rejected: observed not to remove the keys), `FLUSHDB` through the connection factory (equivalent; deleting keys reads more plainly in a test)
[Phase 13] Decision: Redis runs with `--save "" --appendonly no`, no volume, `maxmemory` and `allkeys-lru` | Reason: everything in it can be recomputed from PostgreSQL, so persistence buys nothing and costs fork() pauses and disk — and losing the whole thing is a slow minute, not an incident. A `maxmemory` ceiling with LRU eviction means a full cache drops its coldest key and carries on; `noeviction`, the default, would start failing writes and turn a full cache into an application error | Alternatives considered: persistence enabled (rejected: paying to durably store a derived copy), no maxmemory (rejected: Redis grows until the container limit kills it)
[Phase 14] Decision: The JobRepository is made JDBC-backed by an explicit `BatchConfig extends DefaultBatchConfiguration` | Reason: Spring Batch 6 defaults to `ResourcelessJobRepository`, an in-memory stub, and says nothing about it. Under it every test in this phase passed: jobs ran, counters were right, a completed instance was refused a second time - all from state that dies with the JVM, while the `BATCH_*` tables Flyway created stayed empty. That silently removes the whole reason to use the framework: restart after a crash, "this ran last night", and any record to look an execution up in. Extending the class is what makes Boot's auto-configuration back off (`@ConditionalOnMissingBean(DefaultBatchConfiguration.class)`) | Alternatives considered: a second `JobRepository` @Bean (rejected: two beans named `jobRepository`, and bean overriding is off), `@EnableBatchProcessing` (works, but also disables the auto-configuration and gives less control over the one thing being changed), living with the default (rejected: it is a loop with extra steps)
[Phase 14] Decision: The batch schema is Flyway V7, copied verbatim from Spring Batch's own `schema-postgresql.sql` | Reason: these six tables are production schema - they are where "has this already run?" is answered - so they belong under review and version control like every other table. Boot 4 agrees by omission: unlike Boot 3 it ships no `spring.batch.jdbc.initialize-schema` property at all, so nothing creates them automatically. Verbatim so a future Spring Batch upgrade can be diffed against the jar's copy; the PostgreSQL variant is also valid H2, so one file serves both engines | Alternatives considered: hand-written DDL (rejected: drifts from the framework's expectations invisibly), a schema initializer (rejected: does not exist in Boot 4)
[Phase 14] Decision: V8 indexes `product.name`, and the index is NOT unique | Reason: the import looks every row up by name before deciding insert-or-update, so without an index a 10,000-row file is 10,000 sequential scans of a growing table. Not unique because the API has allowed two products to share a name since Phase 1 and the seed data is unique only by accident - adding UNIQUE would turn an existing, working request into a 500 the first time somebody reused a name. The import therefore updates the OLDEST match (`findFirstByNameOrderByIdAsc`) | Alternatives considered: a unique index (rejected: breaks existing behaviour, outside this phase's scope), a supplier SKU column with a unique constraint (deferred: the honest answer, and a schema change this phase does not own), no index (rejected: quadratic)
[Phase 14] Decision: An upload is staged to disk under a UUID-prefixed name and the job is given that path | Reason: two things at once. A restart re-reads the SAME input BY PATH, and an HTTP request body is gone by the time anyone wants to restart - a job whose input lived only in the request could never be restarted at all. And the path is the import's only identifying job parameter, so a unique name makes each upload its own `JobInstance`; reusing the original filename would make the second upload of `products.csv` a restart of the first, or refuse it outright once the first had completed | Alternatives considered: streaming the multipart straight into the reader (rejected: unrestartable), staging under the original filename (rejected: the second upload is not the same work)
[Phase 14] Decision: Only `InvalidProductRowException` and `FlatFileParseException` are skippable, with a limit of 50 | Reason: "skip bad data" and "swallow bugs" look identical from a distance. `.skip(Exception.class)` would also skip a NullPointerException in the processor and a connection failure in the writer, and the job would report a tidy COMPLETED over a broken system. A narrow exception thrown only by validation keeps the policy honest. The limit turns "a few bad rows are normal" into a number: cross it and the job fails, because a file that is mostly malformed is a different file and not a partial import | Alternatives considered: no skips (rejected: one bad row in ten thousand kills the import), no limit (rejected: 3 rows imported out of 10,000, reported as success), a percentage-based `SkipPolicy` (reasonable; a fixed limit is easier to explain and was enough)
[Phase 14] Decision: Rejected rows are written to `<upload>.errors.csv`, opened and closed per rejection | Reason: a skip limit without an error file is data loss with a counter attached - "COMPLETED, 37 skipped" and nobody can say which 37 or why. Per-rejection open/close because the number of writes is bounded by the skip limit, a listener holding a stream open would need closing on every path out of the step including the failing one, and the partial file then survives a job that dies - which is exactly when somebody wants to read it. Spring Batch calls skip listeners outside the chunk transaction on purpose: a rollback must not erase the record of why a row was rejected | Alternatives considered: a `FlatFileItemWriter` for rejects (rejected: lifecycle to manage for at most 50 lines), logging only (rejected: not something an operator can fix a file from)
[Phase 14] Decision: The import evicts the Phase 13 caches in `afterStep`, never inside the chunk transaction, and only for ids that already existed | Reason: the same evict-before-commit hazard `ProductService.save` describes - inside the transaction the new values are invisible to everyone else, so a concurrent catalogue read could repopulate the cache from the OLD row and be wrong until the TTL. Waiting until the step ends costs a brief window of staleness and buys the guarantee that what lands in the cache afterwards is what is really in the database. Only pre-existing ids because a product the import created cannot have a cache entry. `Cache.clear()` is deliberately not used: Phase 13 observed it report success while the keys survived | Alternatives considered: evicting per chunk (rejected: the repopulation race, times the number of chunks), evicting nothing (rejected: the catalogue would serve the pre-import prices for a full TTL), `clear()` (rejected: observed not to work here)
[Phase 14] Decision: The import runs synchronously and the endpoint answers 200 with the job's status in the body | Reason: Spring Batch's default executor is a `SyncTaskExecutor`, so the response can carry the real counters - which for a catalogue import triggered by a human is what the human wants. 202 Accepted plus polling buys nothing until jobs run long enough for a request to time out, and this one does ten thousand rows in seconds. A 200 means the job RAN; whether it worked is `status`, because collapsing the two would leave nowhere to report a run that completed with rows skipped | Alternatives considered: 202 + a polling endpoint (deferred: the lookup endpoint exists anyway, so this is a small change when jobs get big), mapping FAILED to a 4xx/5xx (rejected: the request succeeded; the job is the thing that failed)
[Phase 14] Decision: The report's summary is a TASKLET step and its best-seller table a CHUNK step | Reason: they are genuinely different shapes and the job is a good place to see why. The summary is two aggregate queries and a few lines of file - done once, one transaction, no stream to iterate, so the chunk machinery would be pure ceremony. The table is a stream: however many products sold that day, read one row at a time from a cursor and written in batches. Ten rows today, more than fits in memory on a real catalogue, and the shape does not have to change for that to be true | Alternatives considered: one tasklet for the whole report (rejected: loses the streaming half of the lesson and does not scale), one chunk step (rejected: a "chunk" of exactly one summary row is a tasklet wearing a costume)
[Phase 14] Decision: The report's date is an identifying job parameter and the scheduler reports on YESTERDAY | Reason: one `JobInstance` per day, so a second run for the same day is refused by the JobRepository rather than quietly rewriting the file - which is what makes `@Scheduled` firing in two application instances safe rather than merely lucky. Yesterday because a job that runs at 02:00 and reports on "today" reports on two hours of it | Alternatives considered: a non-identifying date (rejected: every run a new instance, no protection at all), reporting on today (rejected: two hours of data)
[Phase 14] Decision: `chunk(size).transactionManager(...)`, not the one-call `chunk(size, transactionManager)` | Reason: the two-argument overload builds the pre-6.0 implementation, which Spring Batch 6 deprecates, 7 removes, and which announces itself in the log on every startup. Two observable differences, both caught by the tests: `rollbackCount` is now 0 on a run with skips (the old model rolled the chunk back and replayed it item by item to find the culprit; the new one handles it in place), and a skip-limit failure now surfaces as `FatalStepExecutionException: Unable to process chunk` with the useful sentence further down the cause chain | Alternatives considered: staying on the deprecated API for the clearer message and the rollback counter (rejected: a deprecation note per step on every startup, and removal one major version away)
[Phase 14] Decision: The API reports a failure's whole cause CHAIN, capped at four links | Reason: the framework's outermost exception is almost always the useless one. A skip limit being exceeded arrives as "Unable to process chunk", and what an operator actually needs - "Skip limit of '50' exceeded", then the row that tipped it over - is two links down. Capped so a deeply nested framework failure cannot turn one JSON field into a wall of text | Alternatives considered: the outermost message (rejected: says nothing), the root cause only (rejected: names the last bad row but not the rule that stopped the job)
[Phase 14] Decision: A restart resumes past SKIPPED rows, and the tests say so rather than working around it | Reason: a restart resumes from the last COMMIT. Rows that were read, rejected and committed past are behind that point, so fixing them in the file and restarting does not reconsider them - what a restart recovers is work that was never done, not work that was refused. Those rows are recovered by re-importing the corrected file as a new upload, which is safe because the import upserts. This is the single most surprising thing about restart and it is asserted directly in `ProductImportJobIT` | Alternatives considered: designing the test so the commit boundary hides it (rejected: a test that passes by avoiding the interesting case), re-reading the error file automatically on restart (rejected: invents semantics the framework does not have)
[Phase 14] Decision: The batch directory is a named Docker volume at `/var/lib/ecomdemo/batch`, created in the Dockerfile as the runtime user | Reason: not under `/app`, because the working directory is owned by root and the application runs as `ecomdemo` - the first upload fails on `mkdir` with an error that looks nothing like a permission problem by the time it reaches the client. A volume rather than container-local space because a restart re-reads the staged file by path: an import that failed before a container was replaced could not be resumed if its input had gone with the container | Alternatives considered: `./batch` under `/app` (rejected: permission denied), a bind mount to the host (rejected: makes the stack depend on the host's layout), no volume (rejected: silently unrestartable across a deploy)
[Phase 14] Decision: `spring.batch.job.enabled=false` | Reason: Boot's `JobLauncherApplicationRunner` runs every Job bean it can find once the context is up. That is right for a batch application launched from the command line and wrong for a web application that happens to contain jobs: a restart would re-import whatever file the last upload left on disk, and the sales report would run at boot rather than at 02:00 | Alternatives considered: leaving it on and relying on the JobRepository to refuse completed instances (rejected: it would not refuse an import whose staged path is new, and "it fails safely" is not a design)
[Phase 14] Decision: The sales report has no manual trigger endpoint | Reason: the phase specifies two triggers - an ADMIN upload for the import and a cron for the report - and hard rule 7 says to implement only the phase's scope. The cron is a property, so anyone who wants it now can override `ECOMDEMO_BATCH_SALESREPORTCRON`, and the tests call `BatchService.runSalesReport` directly | Alternatives considered: adding `POST /api/admin/batch/sales-report` (rejected: scope; suggested in the PR instead)
[Phase 15] Decision: Actuator stays on the main port 8080 rather than moving to `management.server.port` | Reason: the phase's concepts are meters, the pull model, RED/USE and liveness-vs-readiness; port separation is a deployment concern and hard rule 7 says to implement only this phase's scope. Keeping one port also keeps the smoke test and the `*IT` tests honest - a management port bound to the internal network could not be reached from either, so the tests would have to be written against a configuration nobody runs. The real reason to separate is recorded in `SecurityConfig` so it is not lost | Alternatives considered: a second port with its own filter chain (deferred: the production answer, and the honest fix for the anonymous scrape endpoint below), Spring Security basic auth for the scraper (rejected: a second credential to manage for one local container)
[Phase 15] Decision: `/actuator/health`, `/actuator/info` and `/actuator/prometheus` are anonymous; everything else Actuator exposes is ADMIN via `EndpointRequest.toAnyEndpoint()` | Reason: every caller of the three is a machine with no credentials - the container HEALTHCHECK, an orchestrator probe, and Prometheus, which carries no token and would need a 15-minute JWT re-issued every 15 minutes for ever. The catch-all rule is written as "any endpoint" and placed last rather than as a list, so an endpoint added to the exposure list later is closed by default instead of open. Matching is by endpoint ID rather than URL because a hand-written `/actuator/health` matcher silently matches nothing if `base-path` moves, and a security rule that fails OPEN when configuration changes is worth avoiding by construction | Alternatives considered: authenticating the scraper (rejected: see above), leaving `/actuator/metrics` anonymous too (rejected: it enumerates everything and is for an operator)
[Phase 15] Decision: `management.endpoints.web.exposure.include` is an explicit four-name allow-list, never `*` | Reason: this list, not an authorization rule, is what makes `/actuator/env` - which prints the environment including `JWT_SECRET` - a 404 even for an administrator. Defence by non-existence beats defence by rule, because the rule is one refactor away from being wrong and the endpoint is not there at all | Alternatives considered: `*` plus exclusions (rejected: a deny-list is wrong by default the moment a new endpoint ships), exposing everything and relying on the ADMIN rule (rejected: `/actuator/heapdump` behind one annotation is a bad trade)
[Phase 15] Decision: Readiness is `readinessState,db`; Redis is deliberately excluded. Liveness is `livenessState` alone | Reason: the single most consequential line of configuration in the phase. The cache is an optimisation - with Redis down every read still works, just slower - so putting it in readiness would take every instance out of the load balancer over a degradation the application can absorb, turning a slowdown into an outage. [Phase 15] Decision: `checkout.duration` is one timer around the whole retry loop, not one per attempt | Reason: a checkout that lost two optimistic locks and succeeded on the third is one thing the customer waited for, not three quick checkouts. [Phase 15] Decision: `percentiles-histogram`, not `percentiles`, and only for `http.server.requests` and `checkout.duration` | Reason: `percentiles` computes p95 inside this JVM, and a percentile from one process cannot be combined with another's - averaging the p95 of three instances gives the p95 of nothing. Buckets cost one time series each, which is why it is an opt-in list and not a global switch, and why explicit SLO boundaries are set for checkout so "how many took longer than a second" is an exact count rather than an interpolation | Alternatives considered: client-side percentiles (rejected: unaggregatable), enabling histograms globally (rejected: cardinality for meters nobody queries)
[Phase 15] Decision: A `MeterFilter` denies any meter tagged with a `/actuator` URI | Reason: Prometheus scrapes every 15s and the container probes every 10s, so without it the busiest endpoint in the shop is the one reporting how busy the shop is - and with the percentile histogram on `http.server.requests`, the scrape's own URI carries a full set of bucket series nobody will ever query. `deny` removes the meter rather than hiding it, so the memory is never allocated. Nothing else is filtered: a meter filter is for cardinality, not for tidiness, and anything dropped is unavailable during the incident when somebody finally wants it | Alternatives considered: filtering in the Grafana queries (rejected: the series still exist and still cost), filtering more broadly (rejected: deleting data to make a dashboard look neat)

A fixed UID because a dashboard that names its datasource by NAME, or by a UID Grafana generated locally, is the usual reason a provisioned dashboard comes up saying "Datasource not found" | Alternatives considered: `allowUiUpdates: true` (rejected: the file and the UI then disagree and the file quietly loses), exporting from the UI after editing (rejected: a workflow nobody follows twice)
[Phase 15] Decision: `DashboardMetricsTest` parses the shipped dashboard JSON and alert rules and fails the build on a metric name the application does not register | Reason: a meter name is a public interface with no compiler behind it. Verified by mutation: renaming the counter in the dashboard, and the timer in the alert rule, each fail the suite | Alternatives considered: trusting review (rejected: the diff looks harmless), a recording rule aliasing old names (rejected: solves the symptom and doubles the series)
[Phase 15] Decision: Prometheus and Grafana live in the main `compose.yaml`, not a separate file like SonarQube's | Reason: SonarQube is a tool run occasionally against a snapshot of the code; monitoring is a runtime companion that is only useful while the application is running, and a dashboard that has to be started separately is one nobody has open when it matters. Both carry their own health checks so `depends_on` ordering is real | Alternatives considered: `compose.monitoring.yaml` (rejected: makes the default `docker compose up` unobservable, which is the opposite of this phase's point)
[Phase 15] Decision: `order.value` is a `DistributionSummary` with no `baseUnit` | Reason: a summary rather than a counter because two questions are asked of the same event - how much revenue (`_sum`) and how large a typical basket (`_count` and the buckets between) - and the average of a stream of numbers is not recoverable from their total. No `baseUnit` because the Prometheus registry folds it into the metric name (`order_value_INR_sum`), which bakes a currency into every dashboard query and into the day the shop sells in a second one | Alternatives considered: a counter of the amount (rejected: cannot answer basket size), setting a currency baseUnit (rejected: renames every series later)
[Phase 16] Decision: JSON logging is switched on by an environment variable (`LOG_FORMAT`), not by a property baked into the build | Reason: the format is a deployment decision. In the container the log is read by Alloy and parsed as JSON, and in that setting the pattern layout is unparseable; on a laptop `./mvnw spring-boot:run` is read by a person, and JSON is a wall of braces per line. One jar, two behaviours, chosen where the application is started - which is the same 12-factor reasoning as the database URL. Spring Boot treats an empty value as "not structured", so the variable being unset is a working default rather than a failure | Alternatives considered: JSON always (rejected: makes local development worse for no gain, since nothing reads it there), a `docker` profile (rejected: the container already runs the `dev` profile, so this would mean a second axis of configuration for one property)
[Phase 16] Decision: Elastic Common Schema (`ecs`), not `logstash` or `gelf`, and no logback-spring.xml at all | Reason: ECS is a published field vocabulary - `log.level`, `error.stack_trace`, `service.name` mean the same thing in every system that speaks it - so the Loki queries and the Alloy pipeline are written against an interface somebody else maintains rather than a private one. Spring Boot has emitted all three natively since 3.4, so the hand-written logback configuration and the logstash encoder dependency that every older tutorial starts with are simply not needed; the whole feature is two properties | Alternatives considered: `logstash` or `gelf` (rejected: each is tied to the tool it is named after, and neither is more useful here), a custom `StructuredLogFormatter` (rejected: a private schema is the thing worth avoiding), logback-spring.xml (rejected: replaces two properties with a file that has to be kept in step with Boot's own defaults)
[Phase 16] Decision: The MDC key is `correlation_id`, flat, while the HTTP header is `X-Correlation-Id` | Reason: the MDC key is written verbatim as a JSON field name, and Boot's ECS formatter turns a DOTTED key into a nested object - `correlation.id` would be emitted as `{"correlation":{"id":"..."}}` and every Loki query, derived field and Alloy expression would have to reach through it. The header keeps HTTP's conventional spelling because that is what a client will send. They are deliberately not derived from each other, so renaming one is a visible change to the other | Alternatives considered: `trace.id` to match ECS's tracing fields (deferred: Phase 23 brings real trace IDs, and claiming the name now would collide), one spelling everywhere (rejected: a hyphen is not legal in a Loki label or a JSON field anyone wants to quote)
[Phase 16] Decision: An inbound correlation ID is validated against `[A-Za-z0-9_-]{8,64}` and REPLACED when it fails, never rejected | Reason: the value arrives in a header and is written into a log line, so it is attacker-controlled text landing in the store that an incident review and possibly an audit will treat as the record of what happened. Without the pattern a caller can send a newline and forge a whole extra log entry, send a megabyte, or send terminal escapes that execute when somebody cats the file. Replacing rather than rejecting because the ID exists for our diagnostics: answering 400 would turn a logging feature into an availability problem for a client that did nothing wrong | Alternatives considered: accepting it verbatim (rejected: log injection), 400 on a bad ID (rejected: breaks clients over a field they do not need to know about), stripping the bad characters (rejected: two different callers can be sanitized to the same ID)
[Phase 16] Decision: `CorrelationIdFilter` is ordered `HIGHEST_PRECEDENCE`, ahead of Spring Security's chain at -100, and sets the response header BEFORE calling the chain | Reason: a request refused with 401 or 403 is answered inside the security chain and never reaches a controller - so a filter ordered after it would leave exactly the requests somebody is most likely to be investigating with no ID in their log lines and no header in their response. The header is set on the way in because headers can only be set until the first byte of the body is written, and the error paths deep inside Spring Security write one | Alternatives considered: a `HandlerInterceptor` (rejected: runs inside the DispatcherServlet, far too late), setting the header after the chain (rejected: silently ignored on any response that has already started)
[Phase 16] Decision: The MDC is cleared in a `finally`, and `shouldNotFilterErrorDispatch()` returns false | Reason: the MDC is a ThreadLocal on a pooled Tomcat thread that is handed straight to the next request. Leaving the ID behind does not lose data - it files the NEXT request's lines under the previous request's story, which is wrong rather than absent and looks entirely normal in the output. The error dispatch is a second pass on the same thread after the `finally` has run, so without the override the most interesting lines of a failing request - the ones written while rendering `/error` - would be the ones with no correlation ID | Alternatives considered: `MDC.clear()` (rejected: removes keys this filter did not put there), clearing only on the happy path (rejected: an exception is precisely when the next request inherits it)
[Phase 16] Decision: `RequestLogFilter` describes a request but never quotes it - no headers, no body, no query string | Reason: each of those is where credentials and personal data live. The `Authorization` header carries a bearer token that is as good as a password until it expires, a login body carries the password itself, and a query string is where an API key ends up when a client takes a shortcut. Logs are replicated, retained after the data they describe is deleted, and readable by people with no business reading customer data, so this is a rule about the destination rather than about any one line. Asserted by tests that send a token, a password and an api_key and require them absent, and by smoke checks that search the live Loki for this run's real credentials | Alternatives considered: logging headers with a deny-list (rejected: a deny-list is wrong by default the first time a new header carries something sensitive), logging bodies at DEBUG (rejected: the level is one property away from being on in the wrong place)
[Phase 16] Decision: `RequestLogFilter` skips `/actuator`, while `CorrelationIdFilter` deliberately does not | Reason: Prometheus scrapes every 15 seconds and the container probes health every 10, so request-logging them is thousands of lines a day that describe no user and explain no incident, consuming the retention window that exists for the lines that do - the same judgement, for the same reason, as the Phase 15 `MeterFilter` that drops Actuator URIs. The ID is still issued for those requests, because a probe that fails is worth investigating and whatever the application logged while answering it should be findable | Alternatives considered: logging them at DEBUG (rejected: a level nobody enables is a line nobody reads, at the cost of the code that writes it), skipping the correlation ID too (rejected: makes probe failures uninvestigable)
[Phase 16] Decision: The correlation ID is Loki STRUCTURED METADATA; only the level and the service name are labels | Reason: a Loki label is the index, and every distinct combination of label values becomes a stream with its own chunks. A correlation ID has one value per request, so as a label it would create one stream per request - millions of tiny streams is the documented way to bring Loki down. As structured metadata it is stored with the line and searched with `| correlation_id = "..."`, which costs nothing to write and is fast enough because the label selector has already narrowed the scan. The level has five values and is what everybody filters on first, so it earns its place in the index | Alternatives considered: correlation_id as a label (rejected: cardinality explosion), the ID only inside the JSON line (rejected: works, but `| json | correlation_id = ...` parses every line in the window, where metadata is matched before parsing), the URI or user as labels (rejected: same cardinality problem, one step less obvious)
[Phase 16] Decision: The application writes to stdout and knows nothing about Loki; Alloy ships the logs | Reason: an application that ships its own logs has to buffer, retry and decide what to do when the log store is down - and both answers are bad. If it blocks, a logging outage becomes an application outage; if it drops, the lines lost are the ones written while something was already wrong. Writing to stdout is a file write that cannot fail interestingly, and the shipping problem moves to a process whose only job it is. Verified by stopping Loki: the application answered 200 with no added latency, and the line written during the outage arrived in Loki after recovery | Alternatives considered: a Loki appender in logback (rejected: puts the network on the logging path of the application), writing to a file and tailing it (rejected: adds a volume and log rotation to solve a problem `docker logs` does not have)
[Phase 16] Decision: Alloy ships only the application, PostgreSQL, Redis, Prometheus and Grafana, named as an allow-list, and never itself or Loki | Reason: Alloy shipping its own log to Loki, and Loki logging that it received it, is a feedback loop that idles at a steady trickle and amplifies the moment either starts complaining about the other. The allow-list rather than "everything except the app" was chosen after running it the other way round: `compose.sonar.yaml` runs in the same Compose PROJECT, so the deny-list quietly swallowed SonarQube and its database too | Alternatives considered: a deny-list (rejected: observed to ship SonarQube), shipping only the application (rejected: the explanation for an application error is sometimes a line PostgreSQL wrote a second earlier, and having to go and find it in `docker logs` is the friction this phase removes)
[Phase 16] Decision: Loki and Alloy have no HTTP health check in compose; Loki has none at all and Alloy's is a bash `/dev/tcp` port check | Reason: not a preference but an inventory. The Loki image is distroless - no shell, no wget, no curl, and Loki itself has no client subcommand - so nothing inside that container can call its own `/ready`, unlike Prometheus which ships `promtool`. The Alloy image has bash but neither curl nor wget, so a port check is the most that can be asked. The real readiness check therefore lives in `scripts/smoke-test.sh`, on the host, where curl exists - and it polls for thirty seconds, because Loki answers 503 until its ingester has joined its own ring | Alternatives considered: adding curl to a derived image (rejected: maintaining a fork of two images to satisfy a health check), `depends_on: service_healthy` for Alloy (impossible without the check, and unnecessary: `loki.write` buffers and retries)
[Phase 16] Decision: Loki's retention is 7 days, and `compactor.retention_enabled: true` is set alongside it | Reason: `retention_period` on its own configures nothing - Loki deletes old chunks only when the compactor is told to apply retention, so a configuration that reads as seven days keeps everything until the disk fills, which is the single most common surprise in a first Loki deployment. Seven days because logs are the most voluminous and least re-read telemetry there is: the line that explains an incident is read within hours, and an audit question belongs in the `order_audit` table rather than in a log store. `LoggingStackConfigTest` fails the build if the two lines are ever separated | Alternatives considered: the Loki default of no retention (rejected: a disk that fills silently), 30 days (rejected: four times the storage for questions this project does not ask)
[Phase 16] Decision: A second dashboard, `EcomDemo Logs`, rather than log panels added to the Phase 15 overview | Reason: the two are used at different moments and by different queries - the overview answers "is something wrong", the logs dashboard answers "what happened to THIS request" - and the phase-15 dashboard has a test asserting its panels' invariants that log panels would have to be carved out of. A textbox variable for the correlation ID makes the "Done when" a paste rather than a hand-written LogQL expression | Alternatives considered: one dashboard (rejected: mixes two questions and complicates an existing test), no dashboard and Explore only (rejected: leaves the phase's acceptance criterion as a thing you have to know how to type)
[Phase 16] Decision: `StructuredLoggingTest` encodes a real ECS document with Boot's own encoder and asserts that every JMESPath expression in `config.alloy` resolves in it | Reason: the same class of silent failure `DashboardMetricsTest` guards in Phase 15, one layer down. The JSON field names are a contract with a file the compiler never reads; rename the MDC key and everything still builds, the application still starts, Alloy still runs - it simply extracts nothing, and the correlation ID stops being searchable until the next incident discovers it. Verified by mutation: renaming the field in `config.alloy`, and widening the derived-field regex in the datasource, each fail the suite | Alternatives considered: asserting on a hand-written JSON fixture (rejected: proves the fixture matches the config, not that the application produces either), trusting review (rejected: the diff looks harmless in both files)
[Phase 16 follow-up] Decision: A checkout evicts both catalogue caches through `@TransactionalEventListener(AFTER_COMMIT)`, not through `@CacheEvict` on the write | Reason: this supersedes the Phase 13 decision above, which recorded transaction synchronisation as the real answer and deferred it as "a phase of its own". Its reasoning about the HAZARD still holds exactly: the checkout write runs once per line inside a transaction that may still roll back, so evicting there discards good entries on every failed checkout and — worse — evicts before the new row is visible, so a concurrent read repopulates the cache from the pre-commit row and is wrong until the TTL, which no later write bounds. What it underestimated was the COST of not doing it: not an abstract staleness but a shopper reading "5 in stock", adding five to a cart and being refused at checkout, for up to ten minutes, with the database correct throughout. AFTER_COMMIT answers the hazard without paying that cost - it runs only if the transaction committed, and only once the new row is visible | Alternatives considered: `@CacheEvict` on save (rejected again, same race, and verified by mutation: putting it back fails `aRolledBackTransactionEvictsNothing`), `@CachePut` of the new value after commit (rejected: the entity is detached by then and the put would race with any transaction that committed in between; an eviction has no value to be wrong about), shortening the TTL (rejected: treats the symptom, multiplies database reads, and still leaves a window)
[Phase 16 follow-up] Decision: `ProductService` publishes a domain event; the eviction lives in the cache package | Reason: ordering has no business knowing that a cache exists, and `ProductService` has no business owning cache mechanics beyond its own annotations. An event lets the catalogue state a fact - this product's stock moved - and leaves whoever cares to react. It is also the shape Phase 17 wants: the same fact is the natural thing to publish to Kafka, and nothing about the publisher has to change for that. The event carries an ID rather than the entity because the listener runs after the commit, when the entity is detached and its persistence context is gone | Alternatives considered: injecting a `CacheManager` into `ProductService` (rejected: puts cache mechanics in domain logic and makes the unit test about caching), evicting from `OrderPlacementService` (rejected: ordering would then know about caching), `TransactionSynchronizationManager.registerSynchronization` by hand (rejected: the annotation is the same thing with less ceremony and a testable listener)
[Phase 16 follow-up] Decision: A cache failure during eviction is logged and swallowed | Reason: it runs after the order has been committed and the customer told it succeeded. Throwing there could not undo the sale and would only turn a completed order into an error response - the worst possible outcome, since the customer would retry a sale that already happened. The cost of a missed eviction is one TTL of staleness, which is the behaviour this whole change removes in the normal case and is not worth failing a sale over. It matches the `CacheErrorHandler` Phase 13 installed for reads and writes | Alternatives considered: propagating (rejected as above), retrying (rejected: the TTL is already the retry, and a retry loop after a commit is a queue nobody drains)
[Phase 16 follow-up] Decision: `scripts/smoke-test.sh` formats metric values with `%.12g`, not `%g` | Reason: found while adding the eviction check. `%g` prints SIX significant digits, so `order_value_sum` at 167656.5 printed as 167656 and a delta that should have been 2499.5 came out as 2499 - a check that had been passing for two phases and would have started failing on its own as soon as the shop's cumulative order value outgrew six digits. Twelve digits covers anything this application produces and still prints 1.0 as "1", which the counter checks compare against | Alternatives considered: `repr()` (rejected: prints "1.0" and breaks the counter checks), `Decimal` throughout (rejected: correct but a larger change to a helper that is already right once the precision is fixed)
[Phase 17] Decision: Kafka runs in KRaft mode, one broker, and every replication factor is written out as 1 | Reason: KRaft removes ZooKeeper entirely - it is gone as of Kafka 4.0, so every `zookeeper:` service in an older tutorial is now wrong rather than merely dated - and one broker is honest about what a laptop is. The internal topics (`__consumer_offsets`, the transaction state log) default to replication factor 3 and fail at the moment they are first needed rather than at startup, which is a confusing way to learn that offsets are themselves a Kafka topic. `REPLICAS` is a named constant in KafkaTopicsConfig with a comment saying what three brokers would change, because it is the first line that differs in any real deployment and nothing in the application code moves with it | Alternatives considered: three brokers in compose (rejected: three JVMs on a laptop to demonstrate a replication factor nobody would exercise), the Confluent images (rejected: `apache/kafka` is the project's own and needs no vendor-specific environment variables)
[Phase 17] Decision: Two listeners - INTERNAL on `kafka:9092` and HOST on `localhost:29092` | Reason: a Kafka client does not keep talking to the address it dialled. It asks for metadata and is told where the partition leaders are, then connects to THOSE addresses - so the broker must advertise an address that is correct from the caller's point of view, and there are two different callers here: the app and Kafka UI on the compose network, and anything the developer runs on the host. One advertised address cannot be right for both. This is the single most common way a first Kafka-in-Docker setup fails, and it fails with a timeout rather than a connection error, because the first connection SUCCEEDS | Alternatives considered: one listener on localhost (rejected: unreachable from other containers), host networking (rejected: not portable to Linux/macOS alike)
[Phase 17] Decision: Topics are created by `NewTopic` beans with `auto.create.topics.enable=false` on the broker | Reason: auto-creation invents a topic with default partitions and replication the moment somebody typos a name, and the typo then looks like it worked - messages go somewhere nobody is reading, which presents as a consumer that is merely slow. Declaring them makes the partition count a reviewed decision rather than a default, and makes the DLT exist from startup, empty, so "is there a dead-letter topic?" can be answered by looking rather than by first causing a failure | Alternatives considered: auto-creation (rejected as above), a topic-creation script (rejected: another thing to run in the right order)
[Phase 17] Decision: The event is a hand-written record, not the `Order` entity, and it is keyed by order id | Reason: a message on a topic is a published contract read by consumers this application does not own and cannot recompile - literally true from Phase 20, and already true of anything reading the topic in Kafka UI. Serialising the entity would publish the JPA version column and whatever a later phase adds, and make a database rename a breaking change for every consumer. The key matters for a different reason: Kafka hashes it to pick a partition and guarantees order only WITHIN a partition, so keying by order id keeps one order's events together and in sequence however many consumers are running. A null key would round-robin them | Alternatives considered: publishing the entity (rejected: couples every consumer to the schema), no key (rejected: gives up ordering for no gain), keying by username (rejected: one hot customer would hot-spot a partition)
[Phase 17] Decision: The event is published from an `AFTER_COMMIT` listener, and the resulting gap is documented rather than papered over | Reason: publishing inside the transaction would announce an order that might still roll back, and a message cannot be un-sent - a consumer would email a customer about an order that does not exist. AFTER_COMMIT is the same shape the Phase 16 cache evictor uses. What it leaves is the DUAL-WRITE problem: between the commit and the send the process can die, leaving an order in the database that nothing was ever published for, and no retry can fix that because nothing knows it is missing. Verified by stopping the broker: the order committed, no notification was ever written, four orders came out of the outage un-notified. The fix is to write the event to the same database in the same transaction and relay it afterwards - the transactional outbox, which is Phase 18's whole subject. Doing it the simple way first is deliberate: the outbox is hard to appreciate until you can point at what it buys | Alternatives considered: publishing inside the transaction (rejected: announces orders that may not exist), Kafka transactions (rejected: they make the Kafka write atomic with other KAFKA writes, not with PostgreSQL - the dual write is unchanged)
[Phase 17] Decision: The publication runs `@Async` on a small bounded pool, and `max.block.ms` is lowered to 5s | Reason: found by the failure test rather than by design, which is why it is recorded here. `KafkaTemplate.send` returns a future and LOOKS asynchronous, but it blocks inside the call until the producer has cluster metadata - up to `max.block.ms`, sixty seconds by default - and the AFTER_COMMIT listener runs on the thread that committed, which is the request thread. With the broker stopped, a checkout returned 201 after 97 SECONDS. Moving the send to its own pool took that to 0.18s, and the lowered block keeps a pool thread from parking for a minute on a broker that is not there. The pool is bounded with an ABORT policy rather than CallerRuns: CallerRuns is the usual advice and is exactly wrong here, because it hands the work back to the request thread - the blocking this exists to prevent | Alternatives considered: leaving it synchronous (rejected: 97-second checkouts), an unbounded queue (rejected: a broker outage becomes an OutOfMemoryError), CallerRunsPolicy (rejected: reintroduces the bug under load)
[Phase 17] Decision: Idempotency is the consumer's job, enforced by a `processed_event` table whose PRIMARY KEY is the event id from the message | Reason: Kafka delivers AT LEAST ONCE and no setting changes that for work done outside the broker - a consumer that writes its row and dies before committing its offset gets the same record again, and so does every consumer in a group after a rebalance. The id must come from the PRODUCER, generated once and travelling with the bytes; an id generated by the consumer or a database sequence would be different for each delivery and would recognise nothing. Making it the primary key rather than a SELECT-then-INSERT moves the check into the database's own uniqueness guarantee, so two consumers racing on the same record do not both pass a check - the second insert is refused. Marker and work are in ONE transaction, because either half alone is worse than neither | Alternatives considered: `enable.idempotence` on the producer (insufficient: it prevents duplicates from PRODUCER retries and says nothing about consumer redelivery), exactly-once semantics with Kafka transactions (rejected: it covers Kafka-to-Kafka, not Kafka-to-PostgreSQL, and this phase should teach the general answer), a SELECT-then-INSERT check (rejected: a race with a gap in it)
[Phase 17] Decision: Retries happen on separate TOPICS via `@RetryableTopic`, not in the consumer thread | Reason: Kafka hands out partitions, not messages, so a consumer that catches an exception and sleeps holds its partition - and everything behind that record waits too. One poison message with a thirty-second backoff stops the whole partition for thirty seconds. Forwarding the failed record to a retry topic and committing the original offset keeps the main partition moving. The cost, which is real: a retried record is no longer in order relative to the ones after it, acceptable for a notification that depends on no other order and NOT acceptable for a sequence of state changes to one aggregate | Alternatives considered: `DefaultErrorHandler` with in-thread backoff (rejected: head-of-line blocking), no retries at all (rejected: a transient database blip would dead-letter an order)
[Phase 17] Decision: Retry topics are suffixed by INDEX, not by delay | Reason: Spring's default names them after the backoff delay - `orders.placed-retry-1000` - which is readable until the delay stops being constant. With jitter it is a different number every start: the first run created `orders.placed-retry-1031` and `-retry-1661`, and every restart would have created two more, for ever, each holding a handful of orphaned messages nothing consumes. `SUFFIX_WITH_INDEX_VALUE` gives `-retry-0` and `-retry-1`, stable across restarts and independent of the backoff | Alternatives considered: dropping the jitter to keep delays constant (rejected: jitter is what stops a thundering herd of records that all failed together retrying together), leaving the default (rejected: unbounded topic creation)
[Phase 17] Decision: `ErrorHandlingDeserializer` wraps the JSON deserializer | Reason: without it a malformed message is a true poison pill. Deserialization happens before any application code runs, so nothing can catch the exception, the record is never processed, the offset is never committed, and the consumer re-reads the same bad bytes for ever - the partition is stopped permanently by one bad message. The wrapper turns it into a failure the listener container can route, which is what makes the poison message end on the DLT rather than hang the consumer | Alternatives considered: catching in the listener (impossible: the failure is upstream of it), a lenient deserializer that returns null (rejected: turns a visible failure into a silent one)
[Phase 17] Decision: Nothing consumes the dead-letter topic | Reason: a DLT is a queue of messages that need a person. Consuming it automatically turns "this message cannot be processed" into an infinite loop with extra steps, and re-driving it without fixing the cause simply refills it. The `@DltHandler` logs at ERROR with topic, partition, offset and key so the record can be found and replayed deliberately - and it takes a raw `ConsumerRecord` with byte values rather than the typed event, because a message on the DLT may well be one that could not be deserialised in the first place | Alternatives considered: an automatic re-drive (rejected as above), no DLT handler at all (rejected: the messages would arrive silently)
[Phase 17] Decision: The integration tests use a real broker in Testcontainers, and the fast suite has Kafka switched off entirely | Reason: the claims this phase makes are about partitions, offsets, consumer groups, redelivery and retry topics, and a test that passes against `@EmbeddedKafka` proves the imitation. Same judgement as Phase 7's PostgreSQL container and Phase 13's Redis. In the Surefire profile `spring.kafka.listener.auto-startup=false` and `spring.kafka.admin.auto-create=false` keep `./mvnw clean test` Docker-free - the second one matters more than it looks: without it KafkaAdmin applied the NewTopic beans at startup and every @SpringBootTest spent forty-five seconds timing out against a broker that was not there | Alternatives considered: `@EmbeddedKafka` (rejected: proves the imitation), a shared broker for the whole build (rejected: tests that share a broker share topics and offsets)
[Phase 17] Decision: The dependency is `spring-boot-starter-kafka`, not `org.springframework.kafka:spring-kafka` | Reason: Boot 4 split its auto-configuration out of the monolithic `spring-boot-autoconfigure` into a module per technology, so the library alone gives the classes and none of the wiring - `KafkaAutoConfiguration` lives in `spring-boot-kafka`. The symptom of getting it wrong is not a missing class but a missing BEAN, "required a bean of type 'KafkaTemplate' that could not be found", which reads like an application mistake rather than a dependency one. The broker image is pinned to `apache/kafka:4.2.1`, the exact `kafka-clients` version Boot 4.1.1 manages | Alternatives considered: the bare library plus a hand-written configuration (rejected: reimplements what the starter already does, and drifts from Boot's defaults)
[Phase 18] Decision: The event is written to an `outbox_event` row in the ORDER's transaction, and a scheduled relay publishes it afterwards | Reason: this supersedes the Phase 17 decision above, which published AFTER_COMMIT and recorded the dual-write gap as deliberate and temporary. That gap was measured, not feared: with the broker stopped, four orders committed and four notifications were never written, permanently. Retries cannot fix it, and that is the part worth sitting with - a retry needs something to retry FROM, and if the only copy of the event was in the memory of a process that has now exited, there is nothing to retry from. The fix cannot be better error handling around the send; the event has to be DURABLE before the send is attempted, and the only storage that can be made durable atomically with the order is the database the order is already being written to. The guarantee changes from "published unless something goes wrong" to "published AT LEAST ONCE, eventually" | Alternatives considered: retrying the send harder (rejected: nothing to retry from after a crash), Kafka transactions (rejected again: they make a Kafka write atomic with other KAFKA writes, not with PostgreSQL), CDC with Debezium (rejected for this phase: it reads the database's replication log and needs no application change at all, which is the better answer at scale and the wrong one to learn first - it moves the problem into infrastructure before the problem is understood, and it publishes row changes rather than domain events)
[Phase 18] Decision: `OutboxWriter.append` is `Propagation.MANDATORY` | Reason: the outbox is worth nothing if the append can run in a transaction of its own - that is the dual write again, one layer down and much harder to see, because the code would look exactly like a working outbox. `REQUIRED`, the default, would silently open a second transaction and produce a system that passes every test and loses events in production. MANDATORY joins the caller's transaction and throws if there is not one, which turns the design into an assertion the runtime enforces. This is the rare case where the stricter propagation is not defensiveness but the specification | Alternatives considered: REQUIRED (rejected as above), a comment saying "call this inside a transaction" (rejected: a convention nothing checks)
[Phase 18] Decision: Two identifiers per row - a BIGINT identity for ordering and a UUID `event_id` for identity | Reason: they are not interchangeable and neither can do the other's job. The sequence is the publication ORDER: the relay reads pending rows by ascending id so events leave in the order they were committed, and `created_at` could not do this because two rows can share a timestamp and a clock that steps backwards would reorder history. The UUID is the IDEMPOTENCY key: it travels in the message, is the same on every republication, and is what `processed_event` matches on the consumer side. Collapsing them would mean either sending a sequence number that only means something in this database, or ordering by a UUID, which has no order | Alternatives considered: one UUID primary key (rejected: no ordering), one sequence only (rejected: a local number cannot be a cross-system idempotency key)
[Phase 18] Decision: `published_at IS NULL` is the entire state machine; there is no `status` column | Reason: a status column can hold 'SENT' with no timestamp, or a typo, and needs a CHECK constraint to stop it. A nullable timestamp cannot be inconsistent with itself - it either records when the row was published or it says it has not been - and it is simultaneously the value the cleanup job filters on. Two facts, one column, no way to disagree | Alternatives considered: `status VARCHAR` plus `published_at` (rejected: two columns that can contradict each other), a separate published table (rejected: a move on every publication, and a second place for a crash to land)
[Phase 18] Decision: The payload is serialised at WRITE time, with the CONSUMER's Jackson 2 mapper rather than Boot 4's auto-configured Jackson 3 | Reason: two separate points. Serialising in the relay instead would mean re-reading entities that may have changed since and publishing the current state under an event claiming to describe a past one - freezing the bytes inside the transaction makes the row a record of a fact, and moves a serialisation failure to where it rolls the order back rather than stranding a row nothing can ever send. The mapper choice is a wire-format requirement: an outbox payload is a Kafka message body and must be written by the mapper that message is READ by, which is `JacksonUtils.enhancedObjectMapper()` behind spring-kafka's `JsonDeserializer`. The two Jackson majors disagree about whether an `Instant` is an ISO-8601 string or an epoch decimal, and a mismatch fails nowhere in the build - it fails at the consumer, at run time, on a message the producer considers perfectly good. [Phase 18] Decision: The relay WAITS for the broker's acknowledgement before marking a row published, and stops the batch at the first failure | Reason: marking a row published because `send()` returned would mark it done while the bytes were still in the producer's buffer, removing the only durable copy from the pending set before it was safe - so the relay blocks on the future, which it can afford because it runs on a scheduler thread that nobody is waiting for. That is the difference from the Phase 17 publisher it replaces. Stopping at the first failure has two independent justifications: ORDERING, because publishing event N+1 after event N has failed puts them on the topic in the wrong order and leaves N to arrive after the event that logically follows it; and COST, because a failure almost always means the broker is unreachable, which is not a property of this event - continuing would spend `max.block.ms` on every remaining row, which at the defaults is over eight minutes of a held-open database transaction achieving nothing | Alternatives considered: fire-and-forget with a callback (rejected: commits the mark before the ack), continuing past a failure (rejected: reorders the topic and hammers a dead broker)
[Phase 18] Decision: An outbox row has no maximum attempt count and no dead-letter state | Reason: the failure it is built for is "the broker is unreachable", which is temporary by nature and affects every row equally. Abandoning a row after N tries would mean the outage this phase exists to survive still loses events - just later, and with a number attached. The `attempts` counter and `last_error` exist to make a stuck row VISIBLE rather than to end it: a row with 400 attempts is an alert, not a state transition. This is the opposite of the consumer-side decision in Phase 17, where a DLT is right because the failure is a property of the message | Alternatives considered: an outbox DLT (rejected: the failure is not the message's fault), silently dropping after N (rejected: loses exactly what the table is for)
[Phase 18] Decision: The cleanup job deletes only PUBLISHED rows older than the retention window, and the `published_at IS NOT NULL` half is load-bearing | Reason: a sweep written as "older than the cutoff" alone would delete pending events precisely because an outage had made them old - deleting the exact rows the phase exists to protect, at the exact moment they mattered, and leaving a system that looks healthy afterwards because the evidence is gone. A pending row is never old enough. The window itself is seven days and is for FORENSICS, not correctness: nothing re-reads a published row, so the number can be an opinion. An outbox that is never swept grows by a row per order for ever, and the table whose whole value is being quick to scan becomes the largest in the database | Alternatives considered: deleting on publication (rejected: no forensics at all, and a delete on the hot path), no cleanup (rejected: unbounded growth), sweeping by age alone (rejected: deletes pending events, and is tested against in both the repository test and the smoke test)
[Phase 18] Decision: The relay's producer is NOT a `KafkaTemplate` bean; `OutboxKafkaSender` owns it privately | Reason: recorded because it was a regression, caught by the smoke test after both other suites were green. [Phase 18] Decision: `SELECT ... So the application stays the public face, exactly as it did for stock in 20b, and the ADMIN rules on writes stay in its SecurityConfig, which is where a human's token actually arrives; catalog-service only ever sees `ecomdemo-app`. THE PROXY IS EXPLICITLY TEMPORARY and the class says so: a per-service proxy hand-written in an application is what an API gateway exists to replace, and Phase 21 is the API gateway. It forwards and does nothing else - no mapping, no business rule, no caching - and the day it acquires one of those it has stopped being a proxy | Alternatives considered: pointing shoppers at catalog-service (rejected: contradicts its own boundary, and changes every public URL), an anonymous read path on catalog-service (rejected: a boundary that depends on who is expected to call it is not one), bringing Phase 21's gateway forward (rejected: a whole phase imported to avoid one forwarding class)
[Phase 20c] Decision: `V14__drop_product.sql` removes the application's copy of the catalogue, rather than leaving it | Reason: the sibling of V13, and the same argument. While the table is still there a query can still read it - a stale repository, a JOIN nobody updated, a report written against the old schema - and all of them would work, return rows, and be wrong, because the data is a frozen copy from the moment of the split drifting further from the truth with every product an administrator edits. Two services reading two copies of one table is the exact failure this phase exists to prevent, and keeping the old copy is the easiest way to cause it. The consequence is honest and was paid immediately: three smoke checks and three migration tests queried that table, and each had to be pointed at catalog_db or moved to catalog-service rather than quietly left passing against stale data | Alternatives considered: leaving the table as a safety net (rejected: a safety net that returns wrong answers is a trap), renaming it to product_old (rejected: the same trap with a label), dropping it in a later phase (rejected: the window where both copies exist is exactly when someone writes the query that reads the wrong one)
[Phase 20c] Decision: The CSV import becomes a distributed write and the partial-failure window is DOCUMENTED rather than closed | Reason: this is the gap the original plan predicted in its §7, now arrived. The import creates products and sets their stock, which is two HTTP calls to two services with two databases and no shared transaction; a failure between them leaves products visible in the catalogue with no stock - unbuyable, and nothing rolls them back. It is accepted for this phase because the honest alternatives are both larger than the problem: a second transactional outbox is a phase of its own, and a saga spanning a ten-thousand-row import is more machinery than a nightly file justifies. What makes it tolerable is a property the import already had for other reasons - it is RESTARTABLE and IDEMPOTENT, keyed on product name, so re-running sets the same levels again and the repair is to run the job rather than to reconcile by hand. The name resolution also moved server-side in the same change: doing it in the caller would have been one HTTP call per ROW to learn an id, an N+1 over the network on the one job built for volume | Alternatives considered: a second outbox in the application (rejected: a phase of its own, and the first outbox exists because an ORDER must be durable - a nightly import does not have that problem), a compensating delete for products whose stock failed (rejected: the compensation can fail too, and it would delete products an administrator may have edited in between), refusing the import unless both services are healthy (rejected: a pre-flight check does not make the window smaller, it just moves it)
