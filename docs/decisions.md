# Decision Log

> One or two lines per decision. Newest at the bottom. Format:
> `[Phase XX] Decision: … | Reason: … | Alternatives considered: …`

[Phase 00] Decision: Merge commits only, no branch deletion | Reason: preserves full phase history and enables ancestry-based merge verification | Alternatives considered: squash merge (rejected: breaks verification)
[Phase 00] Decision: Per-phase docs with a checkpoint file | Reason: keeps each Claude Code session's context small and resumable | Alternatives considered: single roadmap file
[Phase 00] Decision: Repository is public and named `ecomdemo`; the earlier attempt was renamed to `EcomDemo-archive` | Reason: GitHub repo names are case-insensitive, so the old `EcomDemo` blocked the name | Alternatives considered: reusing the old repo (rejected: its `main` already holds ~22 phases of divergent work)
[Phase 00] Decision: Branch protection on `main` with `enforce_admins: true` | Reason: without it GitHub exempts the owner, so "a direct push to main is rejected" would be false for the only person who pushes | Alternatives considered: protection without admin enforcement
[Phase 01] Decision: Spring Boot 4.1.1 on Java 21 | Reason: latest stable 4.x on start.spring.io at the time; Java 21 is the stack's LTS baseline even though JDK 25 is installed locally | Alternatives considered: Boot 4.2.0-M1 (rejected: not GA)
[Phase 01] Decision: Order lines snapshot product name and price, and the order stores its total | Reason: an order is a historical record and must survive repricing or deletion of a product | Alternatives considered: a @ManyToOne to Product with the total derived on read (rejected: rewrites history)
[Phase 01] Decision: The cart total is always derived, never stored | Reason: a stored total is a second source of truth that goes stale when a price or quantity changes | Alternatives considered: a cached total column
[Phase 01] Decision: Lazy associations plus explicit JOIN FETCH queries, and cart writes re-read before mapping | Reason: `save()` on a detached entity merges and returns a copy whose lazy associations are uninitialised proxies, which threw LazyInitializationException; the alternative fix, `@Transactional`, is Phase 6's scope | Alternatives considered: EAGER fetching (rejected: N+1 on every read), @Transactional (deferred to Phase 6)
[Phase 01] Decision: Checkout validates stock for all lines before writing any, but is not yet atomic | Reason: keeps the common failure clean without pulling Phase 6's transaction work forward; the remaining race is the reason Phase 6 exists | Alternatives considered: adding @Transactional now (rejected: out of phase scope)
[Phase 01] Decision: Orders map to table `orders` | Reason: ORDER is a reserved SQL word and an unquoted `insert into order` is a syntax error | Alternatives considered: quoting the identifier everywhere
[Phase 02] Decision: Test at four levels — Mockito unit tests, `@WebMvcTest`, `@DataJpaTest`, and the Phase 1 `@SpringBootTest` | Reason: each slice loads only what it tests, so a failure names its own layer and the suite stays fast (79 tests in ~9s) | Alternatives considered: `@SpringBootTest` everywhere (rejected: slow, and a failure could come from any layer)
[Phase 02] Decision: `MockMvcTester` rather than classic `MockMvc` + Hamcrest matchers | Reason: it is the AssertJ-native MockMvc API in Spring Framework 7, so every assertion in the project reads the same way | Alternatives considered: `mockMvc.perform(...).andExpect(status().isOk())` (rejected: a second assertion vocabulary to learn)
[Phase 02] Decision: Web tests assert the JSON body, not a deserialised DTO | Reason: `BigDecimal.equals()` compares scale as well as value, so a price serialised as 8999.00 and read back as 8999.0 fails an equality check that has nothing to do with the endpoint; JSONAssert compares numbers by value | Alternatives considered: comparing records (rejected: brittle for money), custom comparators (rejected: hides the wire format)
[Phase 02] Decision: `@DataJpaTest` covers only the hand-written `@Query` methods | Reason: everything else on `JpaRepository` is Spring Data's code, and testing a framework's own `findById` adds maintenance without adding confidence | Alternatives considered: testing every repository method
[Phase 02] Decision: Repository tests run with `spring.sql.init.mode=never` | Reason: a repository test should own the rows it asserts on; inheriting `data.sql` would couple the tests to the seed catalogue and break them whenever it changes | Alternatives considered: asserting against the seeded 10 products
[Phase 02] Decision: Generated ids are set reflectively in `TestData` | Reason: several rules key off a product id, and adding `setId()` to the entities purely for tests would let production code invent ids | Alternatives considered: a test-only setter (rejected: weakens the model), mocking the entities (rejected: hides real behaviour like `reduceStock`)
[Phase 02] Decision: Surefire loads the Mockito agent with `-javaagent` | Reason: Mockito self-attaches its bytecode agent today with a warning, and a future JDK will refuse dynamic attachment outright, which would fail the whole unit suite | Alternatives considered: suppressing the warning (rejected: postpones a breakage)
[Phase 03] Decision: springdoc-openapi 3.1.1 | Reason: first GA line built against Spring Boot 4 / Spring Framework 7 (its parent pom builds on Boot 4.1.0); the 2.x line targets Boot 3 | Alternatives considered: springdoc 2.8.x (rejected: wrong Boot generation), hand-written OpenAPI YAML (rejected: drifts from the code)
[Phase 03] Decision: Code-first — the spec is generated from the controllers and DTOs | Reason: one codebase and one author, so a generated document can never disagree with the code it describes | Alternatives considered: contract-first with generated stubs (rejected: its payoff is several teams agreeing on an API before writing code)
[Phase 03] Decision: Document metadata lives in an `OpenAPI` bean (`OpenApiConfig`), not `@OpenAPIDefinition` | Reason: the values are ordinary Java and can later come from configuration or the build, e.g. the version from a release tag | Alternatives considered: the annotation on the application class (rejected: constants only)
[Phase 03] Decision: `@Schema` carries descriptions and examples only; validation rules are not restated | Reason: springdoc already derives `required`, `maxLength` and `minimum` from the Bean Validation annotations, and restating them creates two sources of truth that can disagree | Alternatives considered: spelling out every constraint in `@Schema`
[Phase 03] Decision: Every `@Content` on an error response names `mediaType = "application/json"` | Reason: `@Content` with only a schema documents the body as `*/*`, while `GlobalExceptionHandler` actually returns JSON; the smoke check caught the mismatch | Alternatives considered: leaving the default (rejected: the document would be wrong)
[Phase 03] Decision: The spec is guarded by an automated test as well as the smoke script | Reason: `OpenApiDocumentationTest` fails the build when a controller is added without annotations, instead of waiting for someone to run the smoke test against a live app | Alternatives considered: smoke checks only (rejected: not run by `verify`, and CI arrives in Phase 11)
[Phase 03] Decision: `/v3/api-docs` and Swagger UI stay enabled, accepting springdoc's two startup WARNs | Reason: an explorable API is the point of the phase and there is no production profile yet; springdoc only warns that an open spec reveals the API's shape | Alternatives considered: disabling them (rejected: defeats the phase), a profile switch (deferred: Phase 8 decides access)
[Phase 04] Decision: PostgreSQL 18 from the official `postgres:18-alpine` image, started with one `docker run` | Reason: no installation to undo, the same image the later Docker Compose and Kubernetes phases will use, and the data lives in a Docker volume so it survives container restarts | Alternatives considered: Homebrew PostgreSQL (rejected: machine-specific setup), Docker Compose (deferred: Phase 10 introduces it)
[Phase 04] Decision: The application runs on PostgreSQL but the test suite stays on H2 | Reason: `./mvnw clean verify` must pass on a clean machine with nothing running, and Phase 7 exists precisely to move the tests onto real PostgreSQL with Testcontainers | Alternatives considered: pointing the tests at the same local server (rejected: makes the build depend on a running container three phases early)
[Phase 04] Decision: The `test` profile is activated by surefire's `<systemPropertyVariables>`, not by a `src/test/resources/application.properties` | Reason: an `application.properties` on the test classpath SHADOWS the main one rather than adding to it, so every shared setting in it would be silently lost | Alternatives considered: `@ActiveProfiles("test")` on each test (rejected: easy to forget on a new test), a test-classpath application.properties (rejected: shadowing)
[Phase 04] Decision: Connection details are `${POSTGRES_*:default}` placeholders with throwaway local defaults committed to Git | Reason: the same jar runs anywhere with only environment changes, and a real password arrives as `POSTGRES_PASSWORD` and is never written to a file | Alternatives considered: hard-coded credentials (rejected: cannot be deployed), no defaults (rejected: `./mvnw spring-boot:run` would need a wrapper script)
[Phase 04] Decision: `data.sql` is guarded by `WHERE NOT EXISTS (SELECT 1 FROM product)` as a single statement | Reason: `spring.sql.init.mode=always` re-runs it on every start, and against a database that keeps its rows an unguarded INSERT would add ten more products per restart; one statement means the guard is evaluated once, so it is all ten rows or none | Alternatives considered: `mode=never` after the first run (rejected: manual step, and a fresh database would start empty), one guard per row (rejected: the first insert makes the table non-empty and skips the other nine)
[Phase 04] Decision: H2 runs with `MODE=PostgreSQL` in the test profile | Reason: narrows the dialect gap between what the tests prove and what production runs, at no cost | Alternatives considered: plain H2 (rejected: a wider gap for free)
[Phase 04] Decision: The persistence check spans two smoke-test runs via a `.smoke-state` file | Reason: one run cannot restart the application it is talking to, so the only honest way to prove data outlives the process is to leave a probe behind and look for it after a restart | Alternatives considered: the script restarting the app itself (rejected: it does not own the process), querying PostgreSQL directly with `docker exec` (rejected: couples the script to Docker and a container name)
[Phase 04] Decision: `ddl-auto` stays `update` and the H2 console is removed | Reason: the phase's scope says to keep schema generation until Flyway arrives in Phase 5; the console only ever browsed the in-memory database, and DBeaver, pgAdmin or `psql` replace it | Alternatives considered: `validate` (rejected: there are no migrations yet to validate against)
[Phase 05] Decision: `spring-boot-starter-flyway`, not a bare `org.flywaydb:flyway-core` | Reason: Spring Boot 4 splits auto-configuration into a module per technology, so `flyway-core` alone puts the engine on the classpath with nothing to wire it up — the migrations are silently never run and the application starts against whatever schema it finds | Alternatives considered: `flyway-core` + `spring-boot-flyway` (equivalent, but the starter is the documented entry point), a `FlywayMigrationStrategy` bean (rejected: solves a different problem)
[Phase 05] Decision: V1 reproduces the Phase 4 schema exactly, but with readable constraint names and explicit `ON DELETE` rules | Reason: `ddl-auto=validate` compares tables, columns, types and nullability on every start, so V1 has to match the entities; Hibernate's validator ignores constraint names, foreign keys and indexes, which makes `fk_cart_item_cart` and `ON DELETE CASCADE` free improvements | Alternatives considered: copying `pg_dump` output verbatim (rejected: keeps Hibernate's generated constraint names for ever), hand-writing a different schema (rejected: startup validation would fail)
[Phase 05] Decision: The catalogue seed becomes versioned migration V2, and its `WHERE NOT EXISTS` guard is dropped | Reason: Flyway records that version 2 has been applied and never runs it again, so the idempotency guard Phase 4 needed for `spring.sql.init.mode=always` has nothing left to protect against | Alternatives considered: keeping `data.sql` alongside Flyway (rejected: two mechanisms seeding the same table), a repeatable `R__seed.sql` (rejected: re-runs whenever its checksum changes, which is wrong for rows)
[Phase 05] Decision: V3's `category` column is nullable rather than `NOT NULL DEFAULT` | Reason: expand/contract — during a rolling deploy the migrated schema is live while old instances are still inserting products with no knowledge of the column, and a `NOT NULL` column without a default fails every one of those inserts; tightening it is a later migration's job once every instance writes it | Alternatives considered: `NOT NULL DEFAULT 'UNCATEGORIZED'` (rejected: hides missing data behind a real-looking value), making it required in `ProductRequest` (rejected: breaks existing clients)
[Phase 05] Decision: The test suite runs the same migrations on H2 (`MODE=PostgreSQL`) with `ddl-auto=validate` | Reason: it makes `./mvnw clean verify` fail the moment a migration and the entities drift apart, instead of the next deploy failing to start; it costs nothing and needs no database installed | Alternatives considered: `spring.flyway.enabled=false` for tests with `create-drop` (rejected: the migrations would never be exercised by the build), Testcontainers (deferred: that is Phase 7)
[Phase 05] Decision: The two `@DataJpaTest` repository slices keep `ddl-auto=create-drop` and no Flyway | Reason: `@DataJpaTest` hands each slice its own throwaway database and does not include Flyway's auto-configuration, and these tests are written to own the exact rows they assert on — V2 would seed ten products they never asked for | Alternatives considered: importing `FlywayAutoConfiguration` into the slices (rejected: seed rows leak into query tests), `@AutoConfigureTestDatabase(replace = NONE)` (rejected: the slices would share one database)
[Phase 05] Decision: `baseline-on-migrate=false`, and the Phase 4 database was dropped and rebuilt | Reason: baselining would write a history row for a schema nobody verified and skip straight to the newest migration, so a database built by `ddl-auto=update` would silently differ from one built by V1–V3; on a learning project the data is disposable and a clean rebuild proves the "Done when" outright | Alternatives considered: `baseline-on-migrate=true` (rejected: unverified schema), a `V0__baseline.sql` (rejected: same problem, more files)
[Phase 05] Decision: The smoke test reports a check it could not run as SKIP, counted separately | Reason: the `flyway_schema_history` checks need SQL rather than HTTP, so they depend on a `psql` on PATH or in the container; the testing protocol's honesty rule forbids reporting a check as passed when it never ran | Alternatives considered: passing when psql is missing (rejected: dishonest), failing when psql is missing (rejected: makes the script unusable without Docker), exposing the history over HTTP (rejected: a debug endpoint just for the test)
[Phase 06] Decision: The retry loop (`OrderService.place`) and the transactional unit of work (`OrderPlacementService.placeOnce`) are separate beans | Reason: `@Transactional` is applied by a proxy, so a call from one method of a class to another of the same class never crosses it — a self-invoked `placeOnce()` would run with no transaction at all while looking correct; retrying also *needs* a fresh transaction each attempt, because a failed flush leaves the persistence context unusable and the transaction rollback-only | Alternatives considered: both methods on `OrderService` (rejected: the self-invocation pitfall, silently), injecting the bean into itself (rejected: works, but obscures why), Spring Retry's `@Retryable` (rejected: a second proxy to explain in a phase already about proxies)
[Phase 06] Decision: Optimistic locking (`@Version` on `Product`), not pessimistic | Reason: no lock is taken and no transaction waits; the conflict is detected at write time by `UPDATE ... WHERE id = ? AND version = ?` affecting zero rows, and the loser retries. That is the right trade for a catalogue browsed far more often than it is sold from | Alternatives considered: `SELECT ... FOR UPDATE` (rejected: serialises every checkout of a popular product behind one row lock), SERIALIZABLE isolation (rejected: prevents the same anomaly at far greater cost), a database-level `CHECK (stock_quantity >= 0)` (rejected: turns a business conflict into a constraint violation with no useful message)
[Phase 06] Decision: `order_audit` has no foreign key to `orders`, and `order_id` is nullable | Reason: the row is written with `REQUIRES_NEW`, so it commits while the order's own INSERT is still uncommitted and invisible to it — a foreign key would fail; a REJECTED attempt has no order at all. An audit trail is a log, not a relation: it must be able to outlive and disagree with what it describes | Alternatives considered: a `@ManyToOne` to `Order` (rejected: cannot be satisfied from a separate transaction), writing the audit in the same transaction (rejected: the rejection rolls back with everything else, losing exactly the record worth keeping)
[Phase 06] Decision: The per-line stock pre-check stays, even though the transaction would undo a partial reduction | Reason: failing before any write produces the accurate "requested 3, available 2" message naming the line that is actually short, rather than whichever one happened to break first, and saves the database work it would only throw away | Alternatives considered: deleting it and relying on rollback (rejected: worse errors for no gain), checking only at write time (rejected: same)
[Phase 06] Decision: `CartService` is read-write throughout, `view()` included | Reason: the single shared cart row is created on first use, so even the "read" can insert; `readOnly = true` puts Hibernate into manual flush mode and that insert would be prepared and silently dropped | Alternatives considered: `readOnly` on `view()` with `currentCart()` overriding it (rejected: `view()` calls it internally — self-invocation again, so the outer read-only transaction would be the one in force), returning a transient cart for viewing (rejected: changes behaviour to suit an annotation)
[Phase 06] Decision: `ProductService` declares `@Transactional(readOnly = true)` at class level, with the four writing methods overriding it | Reason: a new read method is then safe by default and a new write method fails loudly if its author forgets to annotate it, rather than the other way round | Alternatives considered: annotating each read (rejected: a forgotten write is the dangerous direction), no class-level default (rejected: same)
[Phase 06] Decision: Three attempts, then `ConcurrentUpdateException` → HTTP 409 | Reason: a retry only helps when the conflict was momentary; three absorbs the one-off collision optimistic locking is designed for and gives up quickly on a stampede, and an exhausted budget is a conflict with current state (409), not a server error (500) — the client can reasonably repeat the request | Alternatives considered: retrying indefinitely (rejected: holds connections while the client waits), no retry (rejected: a single unlucky collision would be a visible failure), 503 + `Retry-After` (rejected: nothing is unavailable)
[Phase 06] Decision: The smoke test fires its two racing checkouts from one `curl` with `--parallel --parallel-immediate` | Reason: two backgrounded `curl` processes each pay ~10 ms of start-up against a ~5 ms checkout, so the second usually arrived after the first had committed — the check passed for the wrong reason and would have kept passing with the locking removed; inside one process the requests genuinely overlap and the versioned UPDATE is rejected on every run | Alternatives considered: two background curls (rejected: does not reliably race), `ab`/`hey` (rejected: another tool to install for two requests)
[Phase 07] Decision: H2 stays; the integration tests are a second suite rather than a replacement | Reason: the two suites answer different questions — "is the Java right?" (120 tests, 9 s, no Docker, run constantly) and "is this true of PostgreSQL?" (15 tests, a container start, run before pushing); deleting H2 would buy honesty in the fast suite at the price of making every inner-loop run need Docker, which is the trade the test pyramid exists to avoid | Alternatives considered: moving the whole suite onto Testcontainers (rejected: slows the loop developers run fifty times a day, and most of those tests never touch SQL), keeping H2 only for the `@DataJpaTest` slices (rejected: an arbitrary line — the `@SpringBootTest` classes are equally about Java, not SQL)
[Phase 07] Decision: The container is a Spring `@Bean` annotated `@ServiceConnection`, not `@Container` with `@DynamicPropertySource` | Reason: Spring then owns the lifecycle (start with the context, stop when it closes) and derives the JDBC url, username and password from the container itself, so no connection string is written in any test and there is no chance of a stale one pointing at a developer's own database | Alternatives considered: Testcontainers' JUnit extension plus `@DynamicPropertySource` (rejected: the test has to copy the random port by hand, and the container's lifetime no longer matches the context's), the JDBC url scheme `jdbc:tc:postgresql:///` (rejected: hides the container in a string, and cannot be configured further)
[Phase 07] Decision: One shared context for every `*IT`, via a single `IntegrationTest` base class | Reason: Spring caches an application context by the annotations that define it, so keeping all of them in one place is what makes the three IT classes share one context and therefore one container — the first class pays ~12 s, the others ~0.1 s; scattering the annotations would silently buy a container per class | Alternatives considered: annotating each IT separately (rejected: one differing annotation is one extra container, with no error to say so), a static container started in a `@BeforeAll` (rejected: hand-rolls what the context cache already does)
[Phase 07] Decision: `withReuse(true)` is deliberately not enabled | Reason: it leaves the container running between builds, and with it the previous run's rows — a build that passes because of yesterday's data is worse than a build that spends another six seconds; the two lines that enable it are documented in `PostgresContainerConfig` for anyone who wants the faster loop | Alternatives considered: enabling reuse (rejected: cross-run state), truncating every table before each class (rejected: reintroduces the cleanup problem reuse was meant to avoid)
[Phase 07] Decision: Failsafe is bound to both `integration-test` and `verify`, not `integration-test` alone | Reason: `integration-test` records a failure but does not stop the build, so that `post-integration-test` always runs and tears down what the tests started; the `verify` goal is what reads those results and fails the build. With only the first goal bound, a failing IT is silently green — this was confirmed with a throwaway failing test | Alternatives considered: binding only `integration-test` (rejected: proven not to fail the build), running the ITs under Surefire by renaming them `*Test` (rejected: `./mvnw test` would then need Docker)
[Phase 07] Decision: The image tag is pinned to `postgres:18-alpine`, matching the dev profile | Reason: an integration test is a claim about a specific engine version; `latest` would make the claim depend on what Docker Hub published that morning, and a version drift between the test database and the dev database defeats the purpose of running the test at all | Alternatives considered: `postgres:latest` (rejected: irreproducible), a digest pin (rejected: unreadable for a learning project, and the tag is already specific)
[Phase 08] Decision: Two migrations — V5 adds `users` and the seeded admin, V6 attaches the cart and the orders to it | Reason: they answer different questions and either could be wanted without the other; splitting them also keeps each file small enough to read as one idea, and V6's three-step `NOT NULL` dance is easier to follow without the table creation above it | Alternatives considered: one V5 doing everything (rejected: two unrelated concerns, and an applied migration can never be split afterwards)
[Phase 08] Decision: The first ADMIN is seeded by a migration, and registration always creates a CUSTOMER | Reason: an anonymous endpoint that accepts a role hands out administrator accounts to whoever asks — the classic privilege-escalation hole; the first admin therefore has to come from something that already has database access | Alternatives considered: a `role` field on `RegisterRequest` (rejected: the hole itself), a bootstrap endpoint that works only while `users` is empty (rejected: a race and a permanent extra endpoint), an env-var-driven `CommandLineRunner` (rejected: puts account creation outside the migration history)
[Phase 08] Decision: The seeded admin's BCrypt hash is written literally into V5, and the password (`admin123`) is documented in the README | Reason: PostgreSQL can hash with pgcrypto and H2 cannot, so a computed hash would make the migration untestable by the fast suite; the credential is a throwaway local development value in the same spirit as the `ecomdemo/ecomdemo` database password already in Git, and the README says plainly that a real deployment changes it first | Alternatives considered: a Flyway placeholder fed from an env var (rejected: the fast suite and the ITs would then need it set too), `pgcrypto` (rejected: PostgreSQL-only, breaks the H2 suite), leaving no admin at all (rejected: nothing could then create a product)
[Phase 08] Decision: ADMIN is refused (403) on `/api/cart/**` and `/api/orders/**` | Reason: those endpoints act on "my" cart and "my" orders, and an administrator has neither; nothing about being an admin implies being a customer, and quietly granting both is how a role system stops meaning anything. It is also the phase file's wording taken literally: "cart and orders require CUSTOMER" | Alternatives considered: `hasAnyRole("CUSTOMER","ADMIN")` (rejected: an admin would silently get a cart), a role hierarchy with ADMIN > CUSTOMER (rejected: implies an admin is a superset of a customer, which is false for ownership-scoped data)
[Phase 08] Decision: Reading another account's order is 403 (`@PostAuthorize`), not 404 | Reason: the phase file allows either; 403 says plainly "that is not yours", where a 404 makes a client think its own order has vanished. It does admit the order exists, which for order ids already visible to their owner is an acceptable trade — for something like a private document it would not be | Alternatives considered: filtering by `user_id` in the query so a stranger's id is a 404 (rejected here, but it is the right default for more sensitive resources — noted in `OrderService.findById`)
[Phase 08] Decision: `@PreAuthorize` for the role, `@PostAuthorize` for ownership | Reason: the rule "this order must belong to the caller" cannot be evaluated before the call, because whose order it is, is in the row; `@PostAuthorize` runs after with the return value bound to `returnObject`. The cost is that the work is already done when the answer is no, so it belongs only on reads — on a write the transaction would roll back but side effects outside it (a log line, an email, a queue message) would not | Alternatives considered: loading the order in the controller and checking by hand (rejected: the check then has to be remembered at every call site), a custom `PermissionEvaluator` (rejected: heavy machinery for one rule)
[Phase 08] Decision: "Only your own orders" is enforced by the query (`findAllByUserIdWithItems`), not by filtering a full result | Reason: filtering after the fact means the method has already read rows the caller may not see, and is one forgotten `filter` away from returning them; putting the owner in the `where` clause means they never leave the database. The repository deliberately has no "load every order" method at all | Alternatives considered: `findAll()` plus a stream filter (rejected: reads other people's data), a Hibernate `@Filter` (rejected: global state that is easy to forget to enable)
[Phase 08] Decision: CSRF protection is disabled | Reason: CSRF attacks ambient authority — a cookie the browser attaches by itself. This API is stateless (`SessionCreationPolicy.STATELESS`), sets no cookie and reads credentials from an `Authorization` header the client must attach deliberately, so a cross-site form arrives with no credentials and is answered 401. The token would protect nothing and break every non-browser client. This reasoning depends on statelessness and must be revisited if cookies ever appear | Alternatives considered: leaving it on (rejected: breaks curl, Swagger "Try it out" and every future service client for no gain), `CookieCsrfTokenRepository` (rejected: same, plus a cookie)
[Phase 08] Decision: 401 and 403 are written by an `AuthenticationEntryPoint` and an `AccessDeniedHandler`, not by `GlobalExceptionHandler` | Reason: a request the security filter chain rejects never reaches the `DispatcherServlet`, so there is no controller, no handler method and no `@RestControllerAdvice` to run — only a `HttpServletResponse` somebody has to fill in. The advice does still handle `AccessDeniedException` for method-security denials, which happen after a controller has been entered | Alternatives considered: relying on the advice alone (rejected: never invoked for URL-level denials), letting Spring Security's empty-body defaults stand (rejected: two statuses with a different contract from every other error)
[Phase 08] Decision: No `WWW-Authenticate` header on a 401 | Reason: it is correct HTTP and it makes a browser pop up its native login dialog — unstyleable, uncancellable and impossible to log out of. The clients here are curl, Swagger UI and the smoke test, none of which need it | Alternatives considered: Spring Security's default `WWW-Authenticate: Basic realm="Realm"` (rejected: the browser dialog)
[Phase 08] Decision: A JPA `User` entity and a separate `AppUserDetails` adapter, rather than making the entity implement `UserDetails` | Reason: the persistence model stays free of framework interfaces and Spring Security stays free of JPA, so either side can change without dragging the other along; the adapter is also where the `ROLE_` prefix is added, keeping that Spring convention out of the database. It additionally carries the account id, which the cart and the orders are keyed by | Alternatives considered: `class User implements UserDetails` (rejected: couples the schema to a framework interface and tempts `getPassword()` into DTOs)
[Phase 08] Decision: `CurrentUser` is an injected bean wrapping `SecurityContextHolder`, not a static call | Reason: services that need "who is calling" stay unit-testable — a test stubs a collaborator instead of populating a thread-local and tearing it down; it also puts the "no authenticated user on this thread" failure in one place, where it can explain itself | Alternatives considered: `SecurityContextHolder.getContext()` inline in each service (rejected: static state in every test), an `@AuthenticationPrincipal` controller parameter threaded down (rejected: every signature grows a parameter that is not part of the domain)
[Phase 08] Decision: `support/WithSecurityRules` imports the real `SecurityConfig` into every `@WebMvcTest` | Reason: `@WebMvcTest` auto-configures Spring Security but does **not** pick up the application's own `SecurityFilterChain` — a slice scans web components and a `@Configuration` class is not one — so the slice silently runs against Boot's fallback "authenticate everything" chain. A test asserting "anonymous gets 401" then passes while proving nothing about the rules that were written | Alternatives considered: repeating a five-class `@Import` in each slice (rejected: noise, and a different import set means a different context cache key and a second context), trusting the fallback chain (rejected: tests the framework's default, not our rules)
[Phase 08] Decision: `@SpringBootTest` classes authenticate as a persisted account via `support/TestAuthentication`, not `@WithMockUser` | Reason: `@WithMockUser` installs a Spring Security `User` principal, but `CurrentUser` needs an `AppUserDetails` carrying the database id — and a fabricated principal names an account that does not exist, so the first `currentUser.require()` fails. Signing in as a row actually in the database keeps the principal, the `users` row and the cart's `user_id` genuinely in agreement | Alternatives considered: `@WithUserDetails` (rejected: still needs the row to exist, and hides where it came from), loosening `CurrentUser` to accept any principal (rejected: weakens production code to suit a test)
[Phase 08] Decision: `ApiErrorWriter` injects Jackson 3's `tools.jackson.databind.json.JsonMapper` | Reason: Spring Boot 4 auto-configures Jackson 3 and defines **no** `com.fasterxml.jackson.databind.ObjectMapper` bean, even though Jackson 2 is still on the classpath via other libraries; injecting the Jackson 2 type fails context startup, and using it manually would format these two responses with a different mapper from every other response | Alternatives considered: `new ObjectMapper()` inside the class (rejected: diverges from the application's configured mapper), hand-writing the JSON string (rejected: an error shape that escapes the type system)
[Phase 08] Decision: V6 deletes the existing cart rows but keeps existing orders, attributing them to the seeded admin | Reason: a cart is scratch state — a few minutes of browsing — and there is no correct account to attribute one assembled by "everyone" to; an order is a financial record and deleting it would throw away the very history the table exists for. The admin is the only account that certainly exists, and inventing a "legacy" user would leave a permanent fiction in `users` | Alternatives considered: migrating the shared cart to the admin (rejected: gives an administrator a cart they never made), deleting the old orders (rejected: destroys history)
[Phase 08] Decision: `orders.user_id` is `ON DELETE RESTRICT`, `cart.user_id` is `ON DELETE CASCADE` | Reason: an order must survive the deletion of the account that placed it, the same way order lines already keep their own copy of the product name and price; deleting a user who has orders now fails, which is the correct answer — that conversation is about anonymising the account, not erasing what was sold. A cart has no meaning without its owner and goes with them | Alternatives considered: CASCADE on orders (rejected: one `DELETE FROM users` erases the sales history), SET NULL on orders (rejected: `user_id` is NOT NULL, and an unattributed order is the state V6 exists to remove)
[Phase 08] Decision: The smoke test's auth plumbing avoids bash arrays | Reason: macOS still ships bash 3.2, where expanding an empty array under `set -u` is an unbound-variable error — so `"${auth_args[@]}"` with no credentials aborts the script on the developer machine this project is written on | Alternatives considered: `#!/usr/bin/env bash` with a `bash >= 4` requirement (rejected: an install step for a smoke test), unquoted word splitting of an `-u user:pass` string (rejected: works only while nothing contains a space)
[Phase 09] Decision: The signing key comes from `JWT_SECRET`, with no default in the repository; when it is unset a random key is generated at startup and a loud WARN is logged | Reason: a signing key in Git is a signing key everybody has, and it is worse to leak than a password because it mints a token for any account with any role — but the phase file also promises the user no manual setup steps, so the application has to start without it. Generating one keeps both promises and fails visibly (tokens die with the process, and a second instance rejects the first's) rather than silently | Alternatives considered: a committed development default (rejected: a secret in Git, and hard rule 9 forbids it), refusing to start without the variable (rejected: a manual step the phase says the user does not have), a key file on disk (rejected: same problem as the default, plus a file to gitignore and forget)
[Phase 09] Decision: A `JWT_SECRET` shorter than 32 bytes fails startup rather than being padded or hashed up to length | Reason: HS256 is HMAC-SHA256 and needs a 256-bit key; quietly stretching a short secret leaves an application running with a weaker signature than its configuration implies, and nothing ever says so | Alternatives considered: SHA-256 the secret to length (rejected: hides a weak input behind a strong-looking key), letting Nimbus fail with its own message (rejected: says nothing about what to do)
[Phase 09] Decision: HS256 (symmetric), not RS256 | Reason: one application both issues and accepts these tokens, so one secret is enough and there is no key distribution to arrange. The trade is written down because it expires: the moment a second service must accept these tokens, giving it the key to verify also gives it the power to issue, and that is the point to move to RS256 with a published public key | Alternatives considered: RS256 with a generated keypair (rejected: key management and a JWKS endpoint are a phase of their own, and nothing yet needs them), an opaque token with server-side lookup (rejected: that is a session, which is the thing this phase exists to contrast with)
[Phase 09] Decision: The token carries `sub`, `uid` and `roles`, and nothing else | Reason: every request after login is authorized from this payload with no database read, so it must carry the account id (the cart and orders are keyed by it) and the roles (the URL rules are decided from them). Nothing more, because a JWT payload is Base64url-encoded and readable by anyone holding the token | Alternatives considered: the whole user record as claims (rejected: publishes the profile to anyone who sees the token, and goes stale), only `sub` with a lookup per request (rejected: reinstates exactly the per-request database read the phase removes)
[Phase 09] Decision: The `roles` claim has no `ROLE_` prefix; the prefix is added by a `JwtGrantedAuthoritiesConverter` on the way in | Reason: `ROLE_` is a Spring Security convention with no business meaning, and a token is a contract with clients — it should not leak the framework we happen to use. Adding it at the converter is also what lets every `hasRole(...)` rule from Phase 8 keep working untouched | Alternatives considered: writing `ROLE_CUSTOMER` into the claim (rejected: framework detail in a public contract), using OAuth2's `scope` claim and `SCOPE_` authorities (rejected: this application thinks in roles, and the rules would all have to be rewritten)
[Phase 09] Decision: `CurrentUser` reads the `Jwt` principal's claims instead of an `AppUserDetails` | Reason: the token IS the source of identity now, and making that visible in the one class that answers "who is calling" is the clearest statement of what changed. It also removes the per-request lookup by username | Alternatives considered: a converter rebuilding an `AppUserDetails` from the claims so nothing downstream changed (rejected: hides the change behind a fake object, and the "id" on it would be a claim pretending to be a database read)
[Phase 09] Decision: The `uid` claim is read as `Number` and narrowed, not cast to `Long` | Reason: JSON has one number type, so a claim written as a `Long` comes back as an `Integer` for small values and a `Long` for large ones — a direct cast works until the users table passes two billion rows, which is the worst kind of bug to ship | Alternatives considered: `getClaim(...)` with a `Long` type parameter (rejected: same ClassCastException, later), writing the id as a string claim (rejected: a number that is not a number)
[Phase 09] Decision: The `AuthenticationManager` bean lives in `auth/AuthenticationManagerConfig`, not in `SecurityConfig` | Reason: the `@WebMvcTest` slices import `SecurityConfig` to get the real rules, and a slice has no `UserDetailsService` bean — keeping the manager out of that class is what lets those slices build a context at all. It is also the more honest split: `SecurityConfig` is about what the filter chain does to every request; this is about one endpoint | Alternatives considered: leaving it in `SecurityConfig` (rejected: every slice fails to start), a `@MockitoBean UserDetailsService` in each slice (rejected: a mock added to make configuration compile, in tests that never authenticate)
[Phase 09] Decision: A 401 distinguishes "no token" from "a token that did not verify", but a login failure never distinguishes a wrong password from an unknown username | Reason: the first distinction is about the bytes presented and helps a client decide whether to log in or log in *again*; the second would be a username-enumeration oracle, letting an attacker find real accounts without guessing a password | Alternatives considered: one message for all four (rejected: a client cannot tell "log in" from "refresh"), Spring Security's own messages passed through (rejected: `UsernameNotFoundException` says exactly the thing that must not be said)
[Phase 09] Decision: No refresh token endpoint | Reason: the phase file lists it as *optional*, and hard rule 7 says to implement only the phase's scope and suggest the rest. Building it properly means a second stored, revocable credential with rotation and reuse detection — a phase's worth of decisions, not an afterthought | Alternatives considered: a quick refresh endpoint that re-issues on any valid access token (rejected: that is just an unlimited expiry with extra steps)
[Phase 09] Decision: Expired-token tests mint a token whose whole lifetime is two hours in the past, rather than using a very short expiry and waiting | Reason: the decoder allows 60 seconds of clock skew, so a "1 second" token is still accepted for another minute — a waiting test would have to burn that minute and would prove less. A token signed with the real key but long expired isolates the clock from the signature | Alternatives considered: a 1-second expiry plus a sleep (rejected: slow and, because of skew, wrong), shrinking the clock skew (rejected: changes production behaviour to suit a test)
[Phase 09] Decision: The smoke test signs its expired token with `JWT_SECRET` when available and falls back to an unsigned one, saying which path ran | Reason: only a correctly signed token proves that *expiry* caused the 401; an unsigned one is refused for the signature instead. The script cannot know the key unless the operator exports it, so it does the strong check when it can and states plainly when it did the weaker one — the testing protocol's honesty rule | Alternatives considered: always unsigned (rejected: silently tests something else), skipping the check without a key (rejected: the weaker check is still worth running), reading the key out of the running process (rejected: not possible, and would be alarming if it were)
[Phase 09] Decision: `LoginRequest` overrides `toString()` to mask the password | Reason: a record's generated `toString()` prints every component, and a request DTO is exactly the kind of object that ends up in a debug log or an exception message | Alternatives considered: relying on never logging it (rejected: one `log.debug("{}", request)` away from a password in a log file)
[Phase 09] Decision: Two `printf`-built JSON bodies in the smoke test instead of inline escaped quotes | Reason: bash 3.2 — still what macOS ships — mis-splits escaped double quotes nested inside a command substitution inside a quoted string, and the body arrived mangled. It surfaced as a 400 where the test expected a 401, which is the dangerous shape of bug: a check that fails for a reason unrelated to what it is checking | Alternatives considered: single-quoted literals (rejected: the username is a variable), requiring bash 4 (rejected: an install step for a smoke test)
